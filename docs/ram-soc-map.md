# RAM и SoC: карта памяти Sigma SMP8645

Собрано по данным, полученным на живом плеере. Проверялось только чтением:
`/proc/devices`, `/proc/meminfo`, `/proc/interrupts`, узлы в `/dev`.

## Зарегистрированные блочные устройства Sigma

`sigmaBlock.c` (`blktrans_open`, `blktrans_ioctl`) регистрирует **11** блочных
узлов, **major 254**:

| узел | размер | что, по всей видимости |
|---|---|---|
| `sigmblocka` | 261 632 КБ = 255,5 МБ | целый банк DDR |
| `sigmblocki` | 80 МБ | — |
| `sigmblockj` | 100,75 МБ | ≈ MM0 (101,94 МБ) |
| `sigmblockp` | 204,25 МБ | ≈ MM1 (203,9 МБ) |
| `b` … `h` | от 256 КБ до 8 МБ | мелкие области |

`sigmblocka = 255,5 МБ` — почти ровно 256 МБ, то есть один банк. Два таких
дают 511 МБ.

Major **252** (`fbxmtdblk*`) **не зарегистрирован** — 16 узлов в `/dev`
устаревшие и пустые. `/dev` доступен для записи, `mknod` возможен.

## Модель памяти

```
Linux RAM   192 МБ   mem=192m, MemTotal 175 МБ
MM0         102 МБ   ruamm0_offset, внутри RAM Linux
MM1         204 МБ   ruamm1_offset, отдельное окно
────────────────────────────
MM0 + MM1   306 МБ   резервы железа
```

Плюс около 77 МБ под MM0 и 52 МБ под MM1 — итого примерно **435 МБ**
адресного пространства под управление.

Содержимое резервов:

* **MM0** — DSP: видеобуферы 65 МБ, аудио, пулы;
* **MM1** — 2D GFX: поверхности, буферы ROMFS, пул DMA 8 МБ.

То есть на вопрос «это DSP или 2D GFX» ответ — **и то и другое**: резервы
принадлежат обоим.

Проверено нами отдельно (`tools/mem_probe.c`): обычной памяти процесса
хватает с запасом — от 256 КБ до **16 МБ** выделяется с записью и проверкой
каждой страницы. Это память, в которую PSP рисует кадр; буфер видеотракта —
другая задача.

## Графические устройства

* `fb0` … `fb3` — четыре фреймбуфера, **char 29**. Это 4 движка GFX.
* `vsync0` … `vsync3` — четыре вертикальные синхронизации, то есть 4 плоскости
  вывода.

## Прерывания и API

* `gfx` — **1 прерывание** за всё время работы. GFX инициализирован при
  загрузке и с тех пор не используется.
* `mum0` — **273 131 прерывание**, это DSP.
* `gbus_*` — API в самом ядре, адреса `0x84006150`–`0x84006570`.
  `em8xxx.ko` его импортирует, то есть `gbus_read_uint32` и есть тот самый
  путь, которым драйвер ходит в регистры.

## Разгадка: sigmblock* — это NAND, а не память

Модуль нашёлся не в `/tango3` (cramfs), а в RAM-rootfs:
`/drivers/nandflash/sigmablock.ko`. Разобран: 15 104 инструкции, 0,5 % мусора.

```
description=NAND Block device driver for connecting NAND flash Library
            and low level device driver
author=Max Lo <max_lo@sdesigns.com>/YH Lin<YH_Lin@sdesigns.com>
```

**Это NAND-драйвер.** Совпадение размеров оказалось случайным: у NAND просто
есть разделы таких размеров, и все девять совпали с таблицей разделов XENV
точно.

| узел | размер | раздел XENV |
|---|---|---|
| `sigmblockb` | 512 КБ | part1 `0x0` + `0x80000` |
| `sigmblockc` | 4 096 КБ | part2 `0x80000` + `0x400000` |
| `sigmblocke/f` | 8 192 КБ | part4/5 |
| `sigmblockg` | 2 560 КБ | part6 `0x14c0000` + `0x280000` |
| `sigmblocki` | 81 920 КБ | part8 `0x1780000` + `0x5000000` |
| `sigmblockj` | 103 168 КБ | part9 `0x6780000` + `0x64c0000` |
| `sigmblockp` | 209 152 КБ | part15 `0x0` + `0xcc40000` |

`l.cs0_size = 0x10000000` = 256 МБ NAND.

### Вариант с `mknod` отменяется сам собой

`/dev/nblock0..15` — это те же устройства, major 254, те же миноры. Узлы
**уже есть**, `mknod` не нужен:

| узел | что на самом деле |
|---|---|
| `nblock8` | `/tango3` (80 МБ, cramfs только для чтения) |
| `nblock9` | `/flashdata` (100,75 МБ) |
| `nblock2` | `/mnt` (4 МБ) |

Отдельные `fbxmtdblk*` (major 252) не обслуживаются — драйвера с таким major
просто нет, `open` возвращает `ENOENT`. Это остатки старой загрузки,
вероятно от проекта 8674.

Итог: читать `sigmblockj` — значит читать `/flashdata`. Тест утратил смысл.

**Писать в `sigmblock*` — это писать в NAND**, что прямо запрещено правилами
проекта. Хорошо, что проверили до `mknod`: мой прежний вывод «потенциально
безопасный доступ к зарезервированной памяти» был неверным.

`blktrans_open` флеш не трогает — мьютекс, аллокация, waitqueue. Но там есть
`schedule_timeout`, то есть **открытие может блокироваться**. NAND-операции идут
в отдельном потоке через `gbus_read_reg8_data` / `gbus_write_reg8_data`.

## Итог по доступу к резервам

| путь | статус |
|---|---|
| `/dev/mem` | обрезан по `mem=192m`, MM1 недоступна |
| блочные устройства | это NAND, а не память |
| `/dev/mum0` + `gbus` | единственный путь, запрещён |
| `EMhwlib*` | только из контекста ядра |

**Безопасного пути к MM0 и MM1 из пользовательского пространства нет. Ни
одного.**

## Что из этого следует для плана

Остаётся **ровно одна гипотеза, и всё держится на ней**: GFX умеет работать
с поверхностью, лежащей в RAM Linux.

Аргумент сильный и берётся из модели памяти: MM0 физически находится внутри
RAM Linux (`0x08D00000..0x0F300000` внутри `0x04000000..0x0FFFFFFF`). То есть
DSP уже читает страницы, которыми владеет Linux. Если так — хватит 33 МБ
`MemFree` под кадр 320×240 (153 КБ) и под всё остальное.

Что ещё следует:

1. **Четыре фреймбуфера и четыре vsync** означают, что игровому кадру есть куда
   попасть без переключения плоскостей, если хватит прав выбора.
2. **`gbus_*` живут в ядре**, из своего процесса напрямую недоступны. Но `shell`
   импортирует их через `em8xxx.ko`, значит рабочий путь — экспорты `shell`,
   как и в случае с `MY_GFX_*`.
3. **GFX почти не используется**: `gfx` — 1 прерывание за всё время, `vsync0..3`
   — 0/1/1/1. Движок инициализирован и простаивает, то есть он свободен и
   никто не завязан на его состояние. Это скорее в нашу пользу.

### Порядок работы с гипотезой

Эксперимент затрагивает запись в регистры GFX, а это уже уронило видео на
живом плеере. Поэтому перед ним нужно:

* **прецедент** — `MY_GUI` уже работает, рисуя в свой буфер;
* **понимание структуры `Command`** — размеры известны по каждому коду
  (`Dune Max/docs/gfx-struct-sizes.txt`), поля нет;
* **вариант без записи в регистры** — отдать GFX уже существующий буфер и
  прочитать результат.
