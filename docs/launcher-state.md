# Лаунчер и рантайм: состояние и что исправлено

## Что было сломано в лаунчере

Всё перечисленное найдено на настоящих файлах, а не предположением.

### 1. Розничные игры не распознавались вообще

`psp_detect_file_type` проверял только `\x7fELF`. Розничный `EBOOT.BIN`
зашифрован схемой `~PSP` и начинается с байт `7e 50 53 50` — это проверено на
реальном образе Magna Carta. То есть лаунчер отдавал файл как
«неизвестный» и не запускал **ни одну** розничную игру.

Добавлена проверка `~PSP`. Рантайм дополнительно сообщает о необходимости
расшифровки вместо того, чтобы падать на разборе ELF.

### 2. `EBOOT.BIN` не извлекался, а образ копировался целиком

`psp_extract_eboot` делал `cp` образа на место `EBOOT.BIN`. На выходе
получался ISO размером в гигабайт, который запустить нельзя.

Разбор ISO 9660 вынесен в переиспользуемый модуль `src/psp_iso.c`
(назначение — `include/psp_iso.h`), потому что он нужен и лаунчеру, и
утилите `iso_extract_eboot`, и расходиться они не должны. Проверенные факты
формата —any-endian поля по 8 байт, `root_dir_record` по смещению 156,
порядок поиска SYSDIR затем USRDIR — закреплены комментариями и
`_Static_assert`.

### 3. Проверка «ISO — игра или фильм» была эвристикой

Стояла проверка «есть ли строка `PSP_GAME` в первых десяти секторах».
Она зависит от того, где именно оказались корневые записи каталога, и даёт
ложный ответ в обе стороны. Теперь критерий — наличие `EBOOT.BIN`, то есть
ровно то, что нужно для запуска.

### 4. Пути не существовали

`/D/PSP_GAMES` на плеере нет, проверено. Рабочий каталог — `/D/psp_launcher`.

### 5. Автозапуск был сломан буквально

В генерируемом скрипте действия стоял литерал `%s` без аргумента
`fprintf`:

```c
fprintf(fp, "        %s/psp-hle \"$FILE\" &\n");
```

Скрипт получался нерабочим: автозапуск не срабатывал ни разу, то есть молча
не работал ровно то, ради чего написан. Теперь путь подставляется при
генерации, добавлена проверка аргумента, а `exec` вместо `&` — чтобы не
терялся вывод рантайма.

### 6. Запуск через `system()`

`system("... &")` плох по трём причинам сразу: `&` отцепляет процесс и его
вывод теряется; имя файла подставляется в строку команды, поэтому пробел или
кавычка ломают запуск, а на плеере такие имена есть; код возврата `system()`
ничего не говорит о том, запустилась ли игра. Заменено на `fork`/`execv`.

### 7. Makefile не соответствовал проекту

Не собирались `guest_load.c` и `pspdecrypt`; `pspdecrypt` не получал
`AES.c` и не линковался; `install` использовал `scp`, который на плеере не
работает. Правила сборки, проверок и доставки переписаны.

Отдельно: `make upload` передавал файлы одной многострочной командой
`smbclient`. Make передавал обратный слэш, `smbclient` выполнял его как
команду — «`\: command not found`», и файлы после первой строки молча не
передавались. Теперь по одному вызову на файл.

## Автозапуск заработал: полный путь на плеере

Проверено на живом устройстве, журнал `/tmp/run/shell.log`:

```
Plugin 'psp_launcher' of type 'plain' is registered
[plugin] psp_launcher: boot action already executed
```

и содержимое `/tmp/psp_launcher_hook.log`:

```
вызов, аргменты: boot
Образ зашифрован схемой ~PSP — расшифровываю.
  расшифровано 5613544 Б, первые байты: 7F 45 4C 46
Модуль      : softmax
Релокаций   : 233235 из 233235 применено
Импортов    : 147 в 18 библиотеках
...
код возврата: 0
```

То есть без всякого ручного запуска: плагин зарегистрирован, хук сработал
сам при старте `shell`, рантайм расшифровал розничный образ, загрузил гостя и
применил все релокации. Дальше — известный блокер входа в гостя.

Флаг `psp_launcher_plugin_boot_action_executed.flag` создаётся в `/tmp/run`
рядом с флагами восьми штатных плагинов. Каталог `/tmp/run` — tmpfs, поэтому
после перезагрузки флага не будет и хук сработает снова.

**Подпись не потребовалась.** У штатных плагинов есть `dune_plugin.sign` (46 Б)
и `dune_plugin_signer_id.txt`, но наш плагин с регистрацией проходит.

## Формат плагина: как он на самом деле устроен

Первая версия лаунчера писала `action.sh` и `plugin.php`. **Такого соглашения у
плеера нет**, и автозапуск не мог сработать никогда. Плеер сообщает об этом
прямо в журнале:

```
[populate_plugins] failed to read plugin manifest from
'/persistfs/plugins/psp_launcher/dune_plugin.xml': No such file or directory
```

Каталог был найден, а манифеста не было. Формат выяснен по штатным плагинам
(`/persistfs/plugins/*/dune_plugin.xml`):

```xml
<dune_plugin>
  <name>psp_launcher</name>
  <caption>PSP</caption>
  <type>plain</type>
  <global_actions>
    <boot>
      <type>plugin_system</type>
      <data>
        <run_string>psp_autostart.sh boot &amp;</run_string>
      </data>
    </boot>
  </global_actions>
</dune_plugin>
```

Что было выяснено по шагам, каждое сообщение плеера:

| что | как обнаружено |
|---|---|
| нужен `dune_plugin.xml` | `failed to read plugin manifest` |
| нужен `<type>` | `invalid plugin manifest ...: type is missing` |
| `<type>plain</type>` вместо `php` | 20 плагинов объявляют `php`, один — `plain`; PHP-класс не нужен |
| хук — `global_actions/boot` | формат взят у `duneext`, у которого `<run_string>bootstrap.sh boot &amp;</run_string>` |
| путь относительный | рабочий каталог — каталог плагина, как у `duneext` |
| амперсанд экранируется | `&amp;` внутри XML |

`dune_plugin_metadata.xml` **необязателен**: у `duneext` его нет, а хук
работает.

Событие об успехе, по которому проверяется установка:
`Plugin '<имя>' of type 'plain' is registered`.

## Перезапуск `shell` — рабочий и безопасный способ

`kill -TERM $(pidof shell)` поднимает новый процесс, он держит Sigma-устройства,
интерфейс восстанавливается. Этим проверяется каждое изменение плагина.

`/tmp/run/child.cmdline` для этого **не годится**: его читает `root` один раз
при своём старте и сам удаляет.

## Что работает на плеере

Полный путь одной командой, как его и вызывает файловый менеджер:

```
sh /persistfs/plugins/psp_launcher/action.sh /D/psp_launcher/games/EBOOT_enc.BIN

  Образ зашифрован схемой ~PSP — расшифровываю.
    расшифровано 5613544 Б, первые байты: 7F 45 4C 46
  Модуль      : softmax
  Гость       : 0x08804000 .. 0x08CA0180 (4833664 Б)
  Релокаций   : 233235 из 233235 применено
  Импортов    : 147 в 18 библиотеках
```

То есть автозапуск доходит до запуска гостя по одному файлу: определение
формата, расшифровка, загрузка, релокации, перечисление импортов.

Проверено отдельно: `install` создаёт плагин, `action.sh` содержит запуск
через загрузчик, `status` отвечает верно.

## Состояние входа в гостя: единственный оставшийся блокер

### Ловушка в стабе работает — это измерено

`tests/trap_probe.c`, изолированная проба на плеере:

| свойство | результат |
|---|---|
| обработчик `SIGTRAP` вызывается | **да** |
| поле адреса инструкции | **`gregs[25]`** |
| запись `$v0` восстанавливается | **да** |
| запись PC восстанавливается | **нет** — `break` выполняется снова |
| `SA_ONSTACK` переключает стек | **нет** |
| подмена инструкции на месте + сброс кэша | **работает**, ровно одна ловушка |

Значит рабочая схема — не сдвиг PC, а замена `break` на `jr $ra; nop` при
первом срабатывании: после возврата процессор перечитывает инструкку по тому
же адресу и выполняет уже подменённую.

### В рантайме падает сам обработчик

```
PC (gregs[25])   = 0x2AAAAC50     ← первая инструкция import_trap, не гость
SP (gregs[29])   = 0x2ABD7CA0     ← гостевой стек, верно
v0               = 0x2AED8000     ← конец отображения гостевого стека
si_addr          = 0x2AED8000     ← то же
$t9              = 0x00000000
```

`si_addr` всегда равен **концу отображения гостевого стека** и следует за его
размером, а не за вершиной гостевого стека: 1 МБ давал `0x2B164000`, 4 МБ —
`0x2B468000`. На MIPS musl кладёт переданное значение `sp` и в `$v0`, и в
`$sp` пути возврата из обработчика. Откуда берётся именно этот адрес — не
установлено: его нет ни в `gregs[29]`, ни в altstack.

Исключено: сборка без PIC (даёт `import_trap` обращение к `0x3D083C` при базе
образа `0x400000`, то есть ниже образа); ассемблерный вход без `$gp`
(`R_MIPS_HI16` по локальному символу в shared-объекте невозможен).

Подробности — `docs/trap-mechanism.md`.

## Как `root` на самом деле выбирает командную строку `shell` (замер 2026-10-06)

Источник — не доки, а собственный лог `root`: **`/tmp/run/root.log`** (упомянут
в `start_firmware.log`: `Starting logging to '/tmp/run/root.log'`). Его нет в
списке файлов документации, но он есть на плеере и читается обычным `cat`.
Формат строки — тот же, что у `shell.log`, но префикс `Root:`.

Дословно из лога:

```
[1135] Root: using shell first-run command line
[1135] Root: starting child 'shell' with command line:
  /firmware/bin/shell first_run
[1135] Root: child process started (pid = 1207)
...
[1135] Root: child process terminated, status = 9
[1135] Root: child exited in 8678 sec
[1135] Root: sleeping 2 seconds before restart
[1135] Root: using shell command line
[1135] Root: starting child 'shell' with command line:
  /firmware/bin/shell
```

Что из этого следует:

- У `root` **два** источника командной строки: «first-run» (с аргументом
  `first_run`) и обычный. Сейчас на плеере второй, и `child.cmdline` отсутствует
  (`cat` → `No such file or directory`).
- `root` **перезапускает потомка сам**, через 2 секунды, и печатает
  `child exited in N sec`. Убийство `shell` — штатная операция, не авария.
- Строка дочерней программы — **`/firmware/bin/shell`**, и она берётся из
  бинарника как строка (`strings /firmware/bin/root` → `/firmware/bin/shell`).
  Значит путь разрешается в момент запуска, и **подмена файла bind-mount’ом
  будет учтена** — это важно для плана «рантайм живёт внутри `shell`».
- `strings /firmware/bin/root` также показывает `config/boot/%s`,
  `/tmp/run/stop_player`, `/tmp/run/power_off`, `/tmp/run/eject_odd_on_boot`,
  `/tmp/run/web_browser`, `/tmp/run/versions.txt`.

Честно не проверено: читает ли `root` `child.cmdline` заново при каждом старте
потомка или один раз при своём старте. В логе видно лишь `using shell command
line` при каждом рестарте, но файла рядом не было. Проверка требует перезапуска
`shell`, то есть кратковременной потери картинки, — **не выполнялась**: на
плеере параллельно работает второй чат, а цена ошибки здесь — потеря видео.

## `.dsf`-механизм и почему он нам не нужен

`dune_service_exec.dsf` (документирован) при выборе в меню «Источники» ищет
`dune_exec` рядом с собой и запускает его. Файл `.dsf` устроен так: подпись
`DUNE SERVICE FILE`, 16 десятичных чисел, нулевая прокладка, затем 341 байт
высокоэнтропийных данных — не zlib/gzip/LZMA по заголовкам, то есть зашифровано.

Проверено на прошивке: **`dune_exec` и ни одного `*.dsf` в `/firmware` и
`/tango` нет**. Значит `dune_exec` — соглашение для пользовательского каталога,
а разбор `.dsf` живёт не в `root`.

Не берём по двум причинам: требует USB-флешки и физического нажатия ENTER на
пульте (хуже, чем SSH, который уже есть), и всё равно не даёт «пути выбранного
файла» в аргументах — а именно это нужно для автозапуска игры.

## Документированный автозапуск `/config/boot/` — и почему его нельзя использовать

`dune_devel_info.html#running_some_code_automatically_on_stb_boot`: исполняемые
файлы из `/config/boot/` запускает процесс `root` при старте, **до старта
`shell`**. Строка `config/boot/%s` в `root` это подтверждает.

Формально это лучший автозапуск из всех: он документирован и срабатывает на
каждой загрузке, тогда как `child.cmdline` читается, по всем признакам, один раз.
Но `/config` — это **flash-раздел**, а по нашим правилам NAND не пишется
ни при каких условиях. Поэтому автозапуск игры держим на своём пути, а этот
канал оставляем записанным как известный, но непригодный.

## Следующие шаги

1. **Путь возврата из обработчика в musl на MIPS.** Это единственное, что
   осталось до исполнения гостя.
2. **`surf` и `fmt` для первого вызова GFX** — они берутся из глобалов, а не
   из аргументов, поэтому из разбора обёртки не получаются.
3. **Реализовать семафоры по-настоящему.** `sceKernelSignalSema` и
   `sceKernelWaitSema` дают 28 % вызовов; без настоящей блокировки потоков
   игра не дойдёт до вывода кадра.
4. **Проверить путь ISO на устройстве** — образа на `/D` нет.

## Замер 89 (сборка bd18dff0, 2026-10-23): база SGS-таблицы и FAULTCAP

Прогон с заправкой SGS через `part_head()` снял старые фолты по адресам 1/2,
но 5 SIGBUS в 0x08AB-зоне остались, а главный поток погиб НОВЫМ способом —
посреди побайтовой заливки. Разбор по дампам кадра и дизасму:

### 1. Формула базы таблицы была с ошибкой +0x40000

Диагностическая формула `((hi & 0xFFFF) + 4) << 16 + sext(lo)` добавляла
`+4` к старшей половине. Релоцированная пара на 0x08AB202C/34 даёт
`hi=0x8BB, lo=0xEFDC` (знаково −0x1024): реальная база =
`(0x8BB << 16) − 0x1024 = 0x08BAEFDC` — .bss внутри RW-сегмента
(0x08B91840..0x08BBB6EC), за file-концом сегмента, т.е. таблица изначально
нулевая. Тот же адрес — в дампе кадра первого сбоя (R20=0x08BAEFDC).

Прежняя база 0x08BEEFDC лежала на 0x40000 выше — в часть-арене
(≥ 0x08BCC000), и заправка уходила впустую.

### 2. Цепочка смерти главного потока

Полная цепочка прогона: пустая таблица → диспетчер аллокатора
(0x08A38180: `метод [T+0x154]/[T+0xD4]`, uncached-трансформация
`0x40000000 | (v0 & 0x1FFFFFFF)` на 0x08A38210-14) получил 0 от обоих
бэкендов → `memset(uncached(NULL) = 0x40000000, 0, 0x13C)` → 316
побайтовых фолтов, каждый честно эмулирован → 129-й превысил общий
FAULT_RECOVER_MAX=128 → `plat_thread_exit()` убил главный поток
(GONE!=08A9C958). Диспетчер вызывался из init-последовательности
Ctrl/Font (ra 0x08A37C7C/84, 0x08A67C68…).

### 3. Исправления в сборке 652ee635

1. Формула базы: `+4u` убрано, заправка идёт в реальную таблицу
   0x08BAEFDC.
2. FAULTCAP: сбои нулевой страницы (`(addr & 0x3FFFFFFF) < 0x10000`)
   больше не входят в бюджет убийства — тот же принцип, что у SPINDEAD;
   бюджет стал на-поток (`g_thread.faults[]`), а не общий на все потоки.

### Ожидание прогона 90

- SGSB печатает 0x08BAEFDC; 5 SIGBUS (0x08AB0C28..0x08AB20AC) исчезают.
- memset 0x40000000 больше не возникает (аллокатор получает валидную
  таблицу); если и возникнет — 316 эмулированных фолтов НЕ убивают поток.
- GONE главного потока (08A9C958) исчезает; звуковой поток (08ACEB98,
  погибавший в замере 89 без единого фолта) — под вопросом: его смерть
  может быть тем же пустым пулом 316-байтных объектов.

## Замер 90 (сборка 652ee635, 2026-10-23, автономное продолжение)

Прогон принёс 184 608 строк отчёта (7 МБ против 10 КБ у прошлого) —
активность выросла в 17 раз. Оба фикса замера 89 сработали:

- `SGSB=08BAEFDC` — правильная база; главный поток **выжил**
  (GONE остался только у звукового `08ACEB98` — и это ЛЕГИТИМНЫЙ
  teardown: в логе прямо перед ним `sceKernelWaitThreadEnd(4)` +
  `sceKernelDeleteThread(4)`, временный поток инициализации звука
  отработал и удалён).

Но фронт сместился, и вскрылись три новые вещи.

### 1. Uncached-зеркало нулевой страницы не было отображено — 65 537 фолтов

Кэшируемая нулевая страница (0x0..0xFFFF) мапилась анонимным блоком,
а uncached-вид 0x4000xxxx — НЕТ. Аллокатор снова вернул NULL (см. п.2),
и `memset(0x40000000, 0, ≥64КБ)` шёл ПОБАЙТОВО через фолт-эмуляцию
43 756 фолтов на одном pc (0x08AD7414 — хвост memset), прошёл весь
первый 64 КиБ и был убит SPINDEAD на границе скретчпада 0x40010000
(зона ≥0x10000 не считается «нулевой страницей»). На PSP это настоящая
память: скретчпад 16 КиБ SRAM на 0x10000 с обоими зеркалами.

### 2. Звуковая подсистема шла по нереализованным вызовам

`unknown_nid=0x1B` — 27 вызовов нереализованных импортов, каждый
получил «0 = успех» дефолта. Среди них ВСЯ звуковая инициализация:
`__sceSasInit(core=0x08BB6F40)`, `__sceSasGetOutputmode`, `__sceSasRev*`,
`sceAudioChReserve` ×4 (каждый получил «канал 0» — четыре раза один!).

### 3. Яд 0xC6600BC0 в таблице 316-байтных объектов

5 SIGBUS зоны 0x08AB остались: walk идёт с базой подобъекта
`0xC6600BC0` — kseg2-подобное значение, которое вообще НЕ может быть
пользовательским адресом. Оно СТАБИЛЬНО между бутами — то есть это
детерминированный мусор: вычисление по нулевому .bss, которое звуковая
инициализация (не прошедшая, см. п.2) должна была заполнить валидными
данными. Игра к моменту walk'а перезаписала наш массив таблицы своим
(.bss-массив 0x08BB0000 — видно в семплере `$a2`), так что заправка
замера 89 для этой таблицы уже не участвует.

Отдельно найден и закрыт прямой вектор: `sceKernelGetThreadId`
возвращал `args[0]` — ЭХО случайного `$a0` вызывающего (у обёртки
0x08AB69A8 аргументов нет) — нарушение правила «возвраты обязаны быть
PSP-истинными».

### Что вошло в сборку ef6da1e7 (не задеплоена — плеер выключен)

1. Нулевая страница + скретчпад `[0x0, 0x14000)` одним tmpfs-файлом в
   ОБОИХ видах (кэшируемый на адресе 0, uncached на 0x40000000):
   записи через любое зеркало видны через другое, как на PSP. Отказ
   любого вида не рушит загрузку (приборы `null_mirror=`/`scr=` в
   отчёте).
2. `sceKernelGetThreadId` — честный uid текущего потока (поиск слота
   по tid), а не эхо `$a0`. uid-ы слотов теперь хранятся.
3. Реализованы: `sceRtcGetCurrentTick` (растущие мкс),
   `sceUtilityGetSystemParamInt` (пишет `*a1`),
   `sceAudioChReserve` (каналы 0..7, все разные),
   `__sceSasInit`/`GetOutputmode`/`RevEVOL`/`RevVON` (параметры Init
   запоминаются и согласованно возвращаются), `sceKernelWaitThreadEnd`.
4. `is_implemented` дополнен остальными вызываемыми (Ctrl sampling,
   Impose, SubIntr, NetInit, Delete*) — счётчик unknown теперь честен.

### Открытые вопросы замера 90

- Происхождение 0xC6600BC0 прослежено до «детерминированный мусор по
  нулям», но не до конкретной инструкции-производителя: ни пара
  lui/addiu, ни R_MIPS_32-слово на массив 0x08BB0000 в образе не
  найдены — адрес вычисляется в рантайме. Оба известных вектора
  (эхо GetThreadId, несостоявшаяся звуковая инициализация) закрыты;
  если значение переживёт сборку ef6da1e7 — нужен дизасм функции
  регистрации массива по факту нового прогона.
- Ожидание прогона 91: шторм 0x4000xxxx исчезает (регион отображён);
  если звуковая инициализация проходит — аллокатор возвращает валидный
  указатель, 5 SIGBUS исчезают, `g_initdone` может поставиться.

## Замер 91 (сборка ef6da1e7, 2026-10-23)

Прогон с маппингом нулевого региона и SAS/Audio-заглушками:

- `unknown_nid=0` — все вызываемые импорты реализованы (пополнение
  `is_implemented` + новые заглушки).
- `null_mirror=0x40000000` — uncached-вид нулевого региона замаплен.
  Побайтовый шторм умер: фолтов **14** вместо 43 761, заливка прошла
  регион на полной скорости и упёрлась в его конец 0x40014000 —
  длина memset ≥ 0x14009 (~82 КиБ), dst по-прежнему
  `0x40000000|0`, то есть аллокатор ВЕРНУЛ NULL.
- `scr=0` — кэшируемый скретчпад 0x10000 не лёг (mmap_min_addr плеера
  выше 0x10000 или адрес занят); uncached-вид есть, игра пишет через
  него.
- Яд `0xC6600BC0` в `$v1` walk'а пережил все три фиксы — идентичен в
  прогонах 88/90/91. 5 SIGBUS зоны 0x08AB на месте.
- Главный поток снова убит SPINDEAD (на 0x40014000), `g_initdone=0`.

Статический поиск производителя яда исчерпан: ни одна пара lui/addiu и
ни одно R_MIPS_32-слово не строят адрес таблицы (0x1D79C) или массива
(0x1E7C0) — оба вычисляются в рантайме через регистры от корня 0x20000
(163 сайта). Решение — диагностическая сборка `2ac0de9e`: при первом
сбое в зоне walk'а обработчик дампит таблицу (`$a1`), массив ([a1+4],
40 слов) и поля менеджера аллокатора 0x08BB7D80+0xC0..0x180 с самими
бэкендами (+0xD4/+0xF0/+0x154/+0x168) — по этому дампу адрес бэкенда
дизассемблируется и выясняется, почему он возвращает 0.

## Замеры 97–99 (2026-10-24): семафоры перевернули boot — игра дошла до звукового движка

### Замер 97→98: CreateSema возвращал 0 всем восьми семафорам

CreateSema был только в is_implemented (дефолт 0): все семафоры игры
получали uid 0, WaitSema/Signal крутились по невалидному uid, блокировки
вырождались, порядок задач рассыпался. Реализованы честные семафоры:
uid-таблица (uid всегда > 0), НАСТОЯЩЕЕ блокирование WaitSема (паки 5 мс
до Signal, клапан 60 с, sema_stuck в отчёте), Signal/Poll/Delete с
PSP-истинными ошибками.

Результат: старая смерть (walk 5 SIGBUS + memset uncached(NULL) +
SPINDEAD) ИСЧЕЗЛА ПОЛНОСТЬЮ. Игра проходит дальше, чем когда-либо:
звуковые зоны 08AB43xx/08AB72xx активны, 16 семафоров создано,
тика-обработчик входит и выходит (SIE/SIX).

### Замер 99: livelock в дренаже звуковых буферов

Прогон зависает: 5 потоков крутятся на 100% (state=R, /proc), отчёт
обрывается без финала. Семплер поймал спин: PC 0x08AB43D8 — цикл
`while (obj->[0x278] > 0) tick(0x08AB6228)` — дренаж незавершённых
аудио-буферов. Тик (0x08AB6228) зовёт 0x08AB2068 — СЕМЕЙСТВО WALK'А ПО
SPARSE-ТАБЛИЦЕ 316-байтных объектов. Таблица по-прежнему пуста — тик
возвращается ни с чем, счётчик не опустошается, все ждут всех.

Насос тика перенесён с паркера на guest_run_wait (пarker — чистый
семплер, заморозка видна вживую). Рукопожатие 0x08A3960C (cond=1 →
тик → отложенная работа) НЕ ВЫПОЛНЯЕТСЯ и после семафорного фикса —
его вызывающий 0x088C3484 не достигается.

### Следующие шаги

1. Кто звонит 0x088C3484 («start sound» → handshake): прямых jal нет,
   вызов косвенный — искать по факту прогона (лог вызовов через
   регистр невозможен — нужен брейкпоинт или дизасм косвенных вызовов

2. Альтернативно: заполнить sparse-таблицу с нашей стороны (по образцу

3. Загадочный поток 0x08AB6798 (entry — обёртка CpuResumeIntr):

4. Livelock лечится рестартом shell (kill -TERM).

## Замер 102 (95e8ff6b): 24 МиБ кучи — спавнер работает, поток завершается штатно

Загадка 0x14000 решена полностью: спавнер 0x08AB67B8 брал 12-байт argp
у игрового аллокатора 0x08A38BD4; при исчерпанной куче (vpl_used 90%)
argp=0, thunk читал func=0 из нулевой страницы, прыгал на 0 и
проскальзывал по nop'ам нулевого региона до 0x14000. GUEST_VPL_BYTES
0xA00000 → 0x1800000 (24 МиБ, как MaxFreeMemSize на PSP).

Результат: поток 0x08AB6798 больше не гибнет — он штатно ЗАВЕРШАЕТ
работу (3 импорта: WaitSema + CpuSuspend/Resume, чистый выход; GONE на
завершившемся потоке — норма, как у module_start).

Остались: livelock поллинга готовности объекта (0x08AB7238 —
аксессуар 0x08AB7228 вхолостую, [obj+0]==0) и повторный дренаж
(0x08AB43DC; клапан замера 100 однократный — дренаж вернулся, DVA
срабатывает снова в каждом прогоне). Bring-up цепочка (рукопожатие
0x08A3960C ← 0x088C3484 ← косвенный вызов) по-прежнему не запускается —
это следующий фронт. Отчёты по-прежнему мерзнут без финальной секции
(заморозка прогона до teardown).

## Замеры 103–103b (f46ea21d, 31be0021): грэйн-комплитер не сработал — семантика поля инвертирована

Окно прогона поднято 600000 → 1800000 (насос умирал на 10-й минуте,
спин дренажа начинается на ~10.5-й). Механика комплитера в бинарнике
подтверждена (GRM-строки, обе ветки), но пометка не прошла ни разу:
условие «маркировать только нулевое [obj+0x27C]» не выполнялось всё
время спина — поле НЕ НУЛЕВОЕ. Вывод: поле ставит сама игра при
постановке грейна (= «поставлен»), а Media Engine должен его
ПОТРЕБЛЯТЬ/обрабатывать (снять и выполнить работу). Верная заглушка —
не ставить поле, а выполнять потребительскую работу за ME.

Следующий шаг (новая сессия): при детекте спина дампить сам объект
дренажа (16 слов от $s0: счётчик 0x278, поле 0x27C, указатели) — по
значениям станет виден точный протокол постановки/потребления грейна;
затем либо вызвать гостевую функцию-потребителя с нашего таймера,
либо воспроизвести её эффект. Направление пользователя: сначала софт-
вызовами, затем оффлоад на DSP аудио / FPU / GFX плеера.
