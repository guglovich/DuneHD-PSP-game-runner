**Зачем нам:** у нас нет своего растеризатора GE — `ge_walk` только классифицирует
примитивы. Теперь есть побитовый эталон, проверенный против настоящего PSP.

**Прямое попадание:** в списке игр, где глубина совпадает побитово, названа
**LocoRoco** — это наш гость.

## 1. Что сделано на стороне PPSSPP

|  | было | стало |
|---|---|---|
| GE | почти точно | 125 из 132 дампов кадров — попиксельно против железа |
| VFPU | таблицы 4.9 МБ (`assets/vfpu`) | ~10.5 КБ коэффициентов, побитово на всех 2^32 входах |

Всё измерено на настоящем PSP: 174 эксперимента с самодельными дисплейными
списками, результат снимался обратным чтением из кадрового буфера и буфера
глубины. Инструмент — `geprobe`: собирает списки на хосте, шлёт в PRX на PSP
по PSPLink, читает обратно.

Эталонная реализация GE: `GPU/Software/GEMath.cpp` + `GEMath.h`, юнит-тесты
`unittest/TestGEMath.cpp`.

Эталонная реализация VFPU: коэффициенты в одном файле, заменяет таблицы fp64.

## 2. Арифметика GE — точные правила

### float24

Параметры дисплейных списков — 32-битные float с отрезанными младшими 8 битами
мантиссы: 1 знак, 8 экспонента, **15 дробных** (16-битная мантисса).

Большая конвейера тоже считает в этой точности. Позиции вершин усекаются на
входе, промежуточные результаты — обратно в float24.

- Всё усечение — **к нулю**, не к минус бесконечности.
- Денормалы ведут себя как ноль.
- Знак и величина хранятся раздельно.

### Сумматор — без защитных битов

```
add(a, b):
    e = max(exponent(a), exponent(b))
    a' = truncate a до кратного 2^(e-15)
    b' = truncate b до кратного 2^(e-15)
    return a' + b'
```

Оба операнда усекаются **до** сложения, а не результат после. Поэтому прибавление
малого к большому теряет младшие биты малого. Видно везде, где есть смещение:
центр вьюпорта, смещение текстуры, конец тумана, `+1` у shade mapping.

### Строка матрицы — это ОДНА сумма

Не цепочка сложений:

1. Каждое произведение формируется точно.
2. Каждый член усекается до кратного наибольшему lsb среди членов.
3. Усечённые члены складываются **точно**.
4. Сумма усекается в float24.

**Порядка нет**, и никакая попарная расстановка скобок не воспроизводит
железо. То же самое делает `vdot` VFPU, но аккуратнее: хранит guard и sticky
биты и округляет итог к ближайшему, а GE просто усекает.

Применяется к: трансформации вершин (все четыре строки), объединению world +
view + projection, скалярным произведениям (`N·L`, `N·H`, квадраты длин),
матрице текстуры, вектору от вершины к источнику света, векторному произведению
касательных Безье.

### Произведение

Точное, затем усечение до веса `2^(ea + eb - 15)`. Когда мантиссы дают 2 или
больше, у произведения остаётся 17-й значащий бит; ниже 2 — 16-й.
Не нормализуется само по себе.

### Обратное (деление)

`z/w` — это `z · R(w)` с усечением, R — линейная интерполяция по **128
сегментам** 15-битной мантисы:

```
s = i >> 8          (сегмент 0..127)
x = i & 255         (позиция внутри)
q = (64·B[s] + 63 + M[s]·x) >> 7      (1/1.i в единицах 2^-16)
```

B от 131072 (1.0) вниз до 65793, M от -254 до -64. Простого порождающего
правила нет — это **хранимая таблица** (`geRecipSegments` в GEMath.cpp).

То же R используется для перспективного деления X, Y, Z, перспективных
текстурных координат, коэффициента интерполяции клиппера ближней плоскости и
затухания точечного света.

**Это не `vrcp` VFPU** — там квадратичная интерполяция.

### Обратный квадратный корень

Нормализация: две таблицы по 128 сегментов, отдельно для чётной и нечётной
экспоненты. `d = 1.i · 2^E`:

```
s = i >> 8,  x = i & 255
table = (E чётная) ? 1/sqrt(1.i) : 1/sqrt(2·1.i)
q = (64·B[s] + 63 + M[s]·x) >> 7
rsqrt(d) = q · 2^-16 · 2^-floor(E/2)
```

Длина вектора — `d2 · rsqrt(d2)`. Нулевой вектор остаётся нулевым.

### Обратное для setup

Деление на удвоенную площадь треугольника — **третья** таблица, мельче: 256
сегментов по старшим 16 битам мантиссы целого:

```
e = floor(log2(absDet))
index = (absDet << 16 >> e) - 65536       (16 бит)
s = index >> 8,  x = index & 255
q = (2·K[s] + M[s]·x) >> 8
```

Почти все K — это `floor(2^39 / (65536 + 256 s) / 16) · 16`, точное значение
в начале сегмента, усечённое до кратного 16. Исключение — сегмент 0 (8388735,
на 127 больше 2^23). M от -257 до -64.

Таблицу сначала подгоняли по пробам, а дозакрыли **играми**: глубине Blade
Dancer понадобился сегмент 39, одному Gouraud-треугольнику со 37 пикселями на
единицу — сегмент 161.

### Растеризация — плоскости в фиксированной точке

Не попиксельная арифметика. Глубина, цвет, туман и текстурные координаты
интерполируются плоскостями:

- Числители плоскости — обычные векторные произведения, позиции вершин в
  фиксированной точке 12.4.
- Градиенты — `floor(n·q / 2^(e+2))`, q и e из setup-обратного. Остаётся 14
  дробных бит на субпиксель.
- Плоскость привязана к одной вершине (см. raster pipeline).
- Значение пикселя — floor плоскости в центре пикселя.

Текстурные координаты идут в плоскости как 15-битные целые: `s`, `t`, `q` каждой
вершины масштабируются до наибольшей экспоненты среди трёх и усекаются до 15
бит. Узкий диапазон UV на большом основании схлопывается по мере исчерпания этих
15 бит.

### Текстурные координаты на пиксель

В transform-режиме `u = s_pixel · R(q_pixel)`, хранится 24 значащих бита,
усекается — это умножение float32 без округления, не float24. В through-режиме
деления нет, координата — 15-битное значение плоскости напрямую.

Координата становится позицией в 1/16 текселя усечением к нулю, поэтому
отрицательная координада выходит на 1/16 выше, чем даёт floor. Для nearest —
`>> 4`, для bilinear — тексель `(k-8) >> 4` и вес `(k-8) & 15`.

### Освещение: pow

Mitchell-аппроксимация над битами float, прямые между степенями двойки:

```
log2(x) = k + (x/2^k - 1)        для x из [2^k, 2^(k+1))
exp2(y) = 2^floor(y) · (1 + frac(y))
pow(x, e) = exp2(e · log2(x))
```

Детали: у экспоненты остаётся 4 бита мантиссы (5.1 работает как 5.0, 1.1 как
1.0625); произведение `e · (bits(x) - bits(1.0))` точное, затем усекается к
кратным 16 в битах; экспонента 0 или меньше даёт 1.0.

Результат никогда не ярче настоящего и на 10–30 ступеней темнее в спаде при
экспонентах 4–64: блики плотнее.

Половинный вектор для specular использует направление взгляда из **третьей
колонки видовой матрицы**, а не (0,0,1). Цвета источников масштабируются
8-битными коэффициентами через `((2x+1)(2s+1)) >> 10` — то же произведение,
что у блендера.

### 8-битные цветовые произведения

```
mul(a, b) = ((2a + 1) · (2b + 1)) >> 10
```

Одна формула для освещения (цвет источника × материал, масштаб каждого члена)
и для блендинга. Фактор f 0..1 сначала становится 8-битным `s = floor(256·f)`
(256 для ровно 1), так что масштаб 1 цвет не меняет.

Удвоенные обратные коэффициенты (`1 - 2α`) — это `255 - 2α` без ограничения: при
α ≥ 128 коэффициент отрицательный, и член вычитается.

### Текстурные функции

- Modulate: `(t · (c + 1)) >> 8` на канал. При удвоении цвета `(2t · (c+1)) >> 8`.
- Билинейная фильтрация — веса по 4 бита: сначала два горизонтальных lerp
  `(a·(16-f) + b·f) >> 4`, усекаются до 8 бит, затем вертикальный, тоже `>> 4`.
- Фрагментная альфа с текстурной: `((a_prim + 1) · a_tex) >> 8`.
- 16-битные тексели сначала разворачиваются до 8 бит на канал, затем фильтруются
  как 8888.

### Туман

Коэффициент считается на вершину, переводится в 8 бит через
`min(floor(256·f), 255)`, интерполируется линейно по экрану. Перспективной
коррекции нет.

### Кривые Безье и сплайны

Оцениваются **без арифметики с плавающей точкой**, хотя все контрольные точки —
float. Каждый lerp — целочисленный: берётся большая экспонента из двух
операндов, оба пишутся как 16-битные целые в единицах младшего бита этой
экспоненты с усечением, затем `A + floor((B - A) · k / 256)` при 8-битном параметре
k/256. При k = 0 и k = 256 операнд пропускается без усечения.

Фиксированная точка выбирается заново для каждого lerp — это блочная плавающая
точка.

### Цвета клипнутых вершин

При создании новой вершины клиппером ближней плоскости цвет и туман —
`(a·(256 - t8) + b·t8) >> 8` при `t8 = round(256·t)`. Позиция и текстурные
координаты — через произведения и сумматор float24.

## 3. VFPU — побитовые функции

Восемь функций теперь считаются из ~10.5 КБ коэффициентов и совпадают с
железом на **всех** 2^32 входах: `vrcp`, `vrsq`, `vsqrt`, `vexp2`, `vsin`,
`vcos`, `vasin`, `vlog2`. Плюс `vrot` (sin+cos вместе).

Структура — классический квадратичный интерполятор: ROM на 128 записей на
функцию, квадратер видит только старшие 10 бит смещения, ширины коэффициентов
подрезаны под точность выхода.

Ключевая деталь, которую не находит наименьшие квадраты: **квадратичный член
округляется до целых ulp отдельно**, до того как прибавляется. Отсюда зубец
ошибки ровно в один ulp.

Для `sin` индексация идёт **с другого конца**: `y = 2^23 − x`. Для `log2`
коэффициенты подрезаются под точность выхода: на уровне d наклон теряет младшие
d+2 бита, квадратичный — младшие d бит величины.

Производительность: 3.6–5.9 нс на вызов против 4.2–14.6 нс у старых таблиц.

## 4. Прямые предупреждения под наш код

| находка | что у нас |
|---|---|
| **Слияние примитивов меняет результат** — у каждого свои плоскости | `ge_walk` не сливает — правильно, теперь с обоснованием |
| **Буфер списка мог завернуться, и GE исполнял устаревшие команды** | у нас обход по указателям; заворачивание надо проверить |
| **Обратное чтение слишком большого размера вешает PSP** | у нас обратного чтения нет, но принцип тот же |
| **Сторонние ошибки выглядят как поведение GE** | гоняли как минимум одну ложную версию — у нас то же |
| **Таблицу сначала подгоняют по пробам, а дозакрывают играми** | у нас нет проб; калибровать по железу нельзя |

## 5. План на нашем плеере

Разделение труда зафиксировано:

- **логика игры исполняется на MIPS CPU** — гость и есть MIPS, нативный плагин
  внутри `shell`;
- **графика уходит в наш GFX** — растеризацию GE делаем сами, результатом
  пиксели в буфер, показ через `MY_GFX_*`.

Растеризатор — по эталону `GEMath.cpp` с его таблицами. Это переводит нас с
«классифицируем примитивы» на «рисуем кадр».

**VFPU — риск:** это сопроцессор Allegrex, у Sigma SMP8642 его нет, значит
первая же такая инструкция даст `SIGILL`, который мы намеренно не пропускаем.
До VFPU-кода гость пока не дошёл. Если дойдёт — перехватываем и эмулируем
побитово по коэффициентам PPSSPP, результат сразу в GFX, чтобы не считать
промежуточное на CPU.

**Объём: 2D и VFPU**, как и раньше. 3D-пайплайн в этом проекте не берём.

## 6. Чек-лист при переносе GEMath

1. Сначала перенести `float24`, сумматор без защитных битов, произведение,
   строку матрицы — это ядро, на нём держится всё остальное.
2. Таблицы `geRecipSegments` (128 сегментов) и setup-обратного (256 сегментов)
   перенести как есть; порождающих правил нет.
3. Порядок строк матрицы — **одна сумма**, без скобок. Проверять юнит-тестом,
   а не глазами.
4. Проверять на 2D-сценах из нашего гостя, а не на синтетике: у PPSSPP
   досегменты дозакрывались именно играми.
5. Юнит-тесты переносить вместе с кодом — `unittest/TestGEMath.cpp`.
