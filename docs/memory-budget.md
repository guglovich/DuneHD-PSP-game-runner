# Память под кадр игры: обычная память Linux

## Вопрос

Хватает ли обычной памяти процесса под кадровый буфер HLE-рантайма:
320×240 в 16 бит, два буфера.

## Ответ: да, с большим запасом

Инструмент: `tools/mem_probe.c`. Память выделяется постранично, **каждая
страница записывается и читается обратно**. Это важно: «MemFree» ничего не
говорит о том, выдаст ли ядро память конкретному процессу, а `mmap` без
записи может вернуть успех, ничем не подтверждённый.

Результат на живом плеере:

```
размер страницы памяти: 16384 Б

кадровый буфер 320x240, 16 бит, буферов 2:
  размер 307200 Б (300 КБ)
  страниц записано и проверено: 18 из 18
  буфер пригоден для чтения и записи

проверка запаса:
     256 КБ — страниц проверено 16 из 16
    1024 КБ — страниц проверено 64 из 64
    2048 КБ — страниц проверено 128 из 128
    4096 КБ — страниц проверено 256 из 256
    8192 КБ — страниц проверено 512 из 512
   16384 КБ — страниц проверено 1024 из 1024
```

Память системы в момент проверки:

```
MemTotal:  179264 КБ
MemFree:    32848 КБ
Buffers:    20896 КБ
Cached:     80304 КБ
```

## Что это значит для плана

* Кадровый буфер 300 КБ берётся без вопросов.
* Запас до 16 МБ выделяется в том же процессе, **все страницы проверены**.
  Этого с избытком хватает и на рабочие структуры гостя.
* `VmRSS` процесса вырос с 480 до 544 КБ после выделения и освобождения
  16 МБ: страницы освобождаются сразу, удержания нет.

Это тот же путь, которым рисует `MY_GUI`: свой буфер в памяти процесса.
Устройства Sigma при этом не открываются, регистры не пишутся, риска,
связанного с инцидентами `docs/bug-dvi-no-video.md`, здесь нет.

## Важное разграничение

Это **не** тот буфер, о котором идёт речь в задаче про 4,3 КБ. Здесь —
память, в которую PSP рисует кадр через `sceGe*` и которая потом отдаётся
на вывод. Буфер, который читает конвейер вывода, — другой вопрос и он
решается отдельно.

## Сколько на самом деле нужно рантайму

| что | размер | источник |
|---|---|---|
| образ гостя (`.text`, `.data`, BSS) | 4,9 МБ | уже выделяется и работает |
| пул трамплинов | 64 КБ | там же |
| кадр 320×240 × 2 буфера | 300 КБ | эта проверка |
| рабочие структуры HLE | десятки КБ | — |

Итого около 1–6 МБ фактически занятой памяти против 33 МБ свободных. Прецедент
играющий — тот же `guest_load`, который уже держит 4,9 МБ по фиксированному
адресу `0x08804000` на живом плеере.

## Оговорка про `shell`

Рантайм планируется внутри процесса `shell`, поэтому память берётся из его
адресного пространства. На момент проверки: `VmSize` 53 МБ, `VmRSS` 23 МБ в
системе на 175 МБ — запас есть. Но это единственное место, где цифры нужно
перепроверить после внедрения: если `shell` растёт, запрос на 16 МБ внутри
него может упереться в его предел, а не в предел системы.

## Побочно подтверждено

Размер страницы памяти на плеере — **16 КиБ**, не 4 КиБ. Это ровно то, из-за
чего все бинарники обязаны собираться с `-Wl,-z,max-page-size=0x4000`. Первая
версия проверки делила длину на 4096 и выдала ложный вывод «часть памяти не
отвечает»; размер страницы надо брать у ядра, а не задавать вручную.
## Фактический расход по трассе `strace --check`

Измерено на плеере (`strace.86xx` 4.5.18), полный путь загрузки без запуска
гостя:

```
mmap(NULL,      65536, RW, MAP_SHARED)                    = 0x2aacc000   разделяемое состояние
mmap(NULL,   5613908, RW)                                 = 0x2aadc000   образ
munmap(0x2aadc000, 5615616)                                              образ освобождён
mmap(0x8804000, 4915200, RWX)                             = 0x8804000    гость
mmap(NULL,    538832, RW) / mmap(NULL, 134723, RW)                       рабочие буферы
munmap обоих
mmap(NULL,    393888, RW) / mmap(NULL, 114688, RW)                       второй проход
munmap обоих
munmap(0x8804000, 4915200)                                             выход
```

**Пик — около 6,3 МБ, утечек нет.** Освобождение образа сразу после загрузки
гостя обязательно: держать его до конца прогона при `MemFree` 10–17 МБ — риск
нехватки памяти под стеки гостя.

Ограничение: `strace` на полном запуске **зависает** (родитель в `wait4`,
потомок не завершается) — механизм ловушек через `break` несовместим с
ptrace. Для проверки пути загрузки используется режим `--check`, где гость не
исполняется.
