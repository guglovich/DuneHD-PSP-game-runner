# Загрузчик гостевого модуля PSP

## Что сделано

`src/guest_load.c` + `include/guest_load.h` грузят расшифрованный `EBOOT.BIN`
в память плеера и готовят его к запуску:

1. отображение по базе `0x08804000` — настоящей базе пользовательской памяти
   PSP; плюс пул трамплинов сразу за сегментом;
2. копирование сегментов `PT_LOAD` с обнулением BSS;
3. применение релокаций PRX;
4. сброс instruction cache;
5. перечисление импортов и подмена стабов.

Проверено на настоящем модуле (Magna Carta / ULJS00042) и на хосте, и на
плеере — результаты совпадают побайтово.

```
=== релокации ===
        всего: 233235
        применено: 233235
        неподдержанных типов: 0
        без пары HI16/LO16: 0
        с неверным сегментом: 0

=== импорты ===
        библиотек: 18, импортов: 147

=== проверка результата релокаций ===
        .data: 730712 байт, проверено значений: 182678
        указывают внутрь гостя: 39754 (21.8%)

=== подмена стаба ===
        стабов пропатчено: 147 из 147
```

21.8 % — это ожидаемо: `.data` на 730 КБ содержит не только указатели, но и
числа, строки и таблицы. Прежде исправления релокаций доля была 0.0 %.

## Три грабли, каждая молча даёт «всё прошло, но неверно»

### 1. Тип секции релокаций — `0x700000A0`, а не `9`

```c
#define GUEST_SHT_REL 0x700000A0u   /* НЕ SHT_REL (9) */
```

PSP использует собственный тип в диапазоне LOPROC. Со значением `9` загрузчик
находит **ноль** релокаций, не падает, не ругается — а все внутренние указатели
остаются неверными. Обнаруживается только первым вызовом гостевого кода.

Проверка: на секцию `.rel.data` приходится 98 467 релокаций, `.rel.text` — 134 703.

### 2. После релокаций указатели уже абсолютные

Соблазн: взять `stub_top` из сведений о модуле и прибавить базу. Неверно.

Релокации покрывают ровно те поля, которые кажутся «виртуальными адресами»:

| секция | релокаций | что это |
|---|---|---|
| `.rel.rodata.sceModuleInfo` | 5 | `gp`, `ent_top`, `ent_end`, `stub_top`, `stub_end` |
| `.rel.lib.stub` | **54** | по 3 на запись × 18 библиотек |

54 = 18 × 3 — это и есть доказательство, что в каждой записи таблицы стабов
релоцируются все три указателя (имя библиотеки, таблица NID, таблица стабов).
После применения релокаций они уже содержат абсолютные адреса, и второе
прибавление базы уводит их за пределы отображения.

Ошибка проявляется как «запись импортов выглядит неверно: count=4» — то есть
отвергается perfectly valid библиотека `sceUmdUser` с четырьмя импортами.

**Как разведено у нас:** сведения о модуле снимаются **один раз, до релокаций**
(`m->info`, `m->has_info`) и хранятся в виртуальной форме; сама таблица стабов
читается из памяти уже после релокаций и трактуется как абсолютная. Границы
берутся из отображения, а не из `info->stub_*`.

### 3. Значение LO16 надо читать до применения любых патчей

Пары `HI16`/`LO16` считаются вместе:

```
value = (HI16 & 0xFFFF) << 16
value += (int16)(LO16 & 0xFFFF)
value += адрес сегмента-цели
HI16  = (HI16 & 0xFFFF0000) | ((value - (int16)(value & 0xFFFF)) >> 16)
```

Если идти по таблице один раз и читать LO16 из памяти, то к моменту обработки
пары там может лежать уже исправленное значение — и получаются указатели,
уехавшие на 64 КиБ. Поэтому запись разбирается в два прохода: сначала
проверка адресов и запоминание исходных слов, потом применение.

Пропуск шага вычитания знаковой младшей половины даёт ту же ошибку, но
смещение всегда одно и то же, что удобно и опасно: выглядит как «почти
работает».

## Трамплины: почему `j` недостаточно

Стаб импорта — 8 байт, это `j` + слот задержки. У `j` непосредственный
операнд 24 бита, а старшую четверть процессор берёт из `$pc`, то есть цель
должна лежать в том же 256 МБ сегменте. На настоящей PSP гостевой код и ядро
лежат рядом (`0x08804000` и `0x08800000`), поэтому достаточно `j`.

У нас хостские функции лежат в другом сегменте (0x2aaa…, 0x7fb6…, 0x522d… —
зависит от того, как загрузилась musl), и `j` не годится. Схема:

```
стаб:     lui $t9, hi(трамплин) ; jr $t9 ; nop
трамплин: lui $t9, hi(цель)     ; jr $t9 ; addiu $t9, $t9, lo(цель)
```

`addiu` стоит в слоте задержки `jr`, поэтому полный 32-битный адрес успевает
собраться до перехода.

**Трамплин обязан лежать внутри отображения гостя.** Первая версия писала его
по адресу `(stub & ~0xFFF) - 0x1000` — то есть в произвольную память, где
могут лежать гостевые данные. Теперь пул идёт сразу за сегментом, в том же
256 МБ сегменте, по 16 байт на подмену, с проверкой исчерпания.

## Сброс instruction cache обязателен

Отдельная находка, см. `icache-finding.md`: без `__builtin___clear_cache`
процессор MIPS исполняет из кэша команд и достаёт мусор вместо только что
записанного. Загрузчик ядра сбрасывает кэш сам — поэтому `dlopen` работал, а
собственная память нет.

## Чего загрузчик не делает

Точку входа не вызывает. Гостевой код сразу рассчитывает на полноценную ОС PSP:
создание потоков, системные вызовы, TLS. Без неё падение на первом же вызове
ничего не скажет о загрузчике — только о том, что подменять надо по порядку,
начиная с `sceKernelCreateThread` и `sceKernelStartThread`.
