# Падение `strncmp(NULL, "disc0:", 6)`: загрузочные аргументы гостя

Дата разбора: 2026-10-14. Сборка, на которой разобрано: `3d1bc70a`
(GetBlockHeadAddr уже возвращал адрес внутри образа гостя, abort
`.cplinit` уже устранён).

## Симптом

Стабильный, единственный сбой прогона:

```
pc=08AD7788  (vaddr 0x2D3788, внутри strncmp на 0x2D3764)
инструкция: lb $a3,0($a0)   (слово 0x80870000)
$a0=0, $a1=0x08B0F5D4 (строка-константа гостя, vaddr 0x30B5D4)
$ra=0x088C1298 (вызов из F, vaddr 0xBD1FC)
```

До сбоя гость успевал: 6× `sceUtilityLoadModule` с ID
`0x0100,0x0101,0x0300,0x0301,0x0302,0x0303` (совпали с таблицей на
vaddr `0x30B548` байт в байт), затем падал на первом из трёх сравнений
`argv[0]` с префиксами устройств.

## Цепочка (весь путь измерен и разобран, шаг за шагом)

1. `e_entry` гостя = vaddr `0x298844` (runtime `0x08A9C844`) — это
   `module_start(SceSize args, void *argp)`. Он пересылает СВОИ `(a0,a1)`
   в `sceKernelStartThread` на местах `(arglen,argp)` без изменений:

   ```
   08A9C920: move $a1,$s3   ; $s3 = module_start.a0 = arglen
   08A9C924: jal  StartThread
   08A9C928: move $a2,$s2   ; $s2 = module_start.a1 = argp
   ```

   Попутно измерено там же: приоритет `*(0x327FE0)=0x14`, размер стека
   `*(0x327FDC)<<10 = 0x40000` — совпадает с кольцом вызовов.

2. Точка входа главного игрового потока — vaddr `0x298958`
   (runtime `0x08A9C958`), контракт `main`-типа: режет блок `argp` по
   `'\0'` в массив `argv[0..19]` НА СВОЁМ СТЕКЕ (`$sp+0..$sp+0x4C`),
   терминирует нулём, считает `argc` и зовёт `G(argc, argv)`:

   ```
   08A9C9A8: blez $s3 → пропуск разбора при пустом блоке
   08A9C9B4: sw $s0,($s1)   ; argv[i] = строка
   ...       цикл до 20 строк, граница — arglen
   08A9C9FC: sw $zero,($t0) ; argv[argc] = NULL
   08A9CA5C: move $a0,$s4   ; argc
   08A9CA60: jal 0xBF2AC    ; G(argc, argv)
   08A9CA64: move $a1,$sp
   ```

3. `G` (0xBF2AC) просто перепроставляет `(a0,a1)` дальше: `jal 0xBEE6C`.

4. `F` (0xBEE6C) — то же самое, до `sceUtilityInit`:

   ```
   088C2F64: jal 0xBD1FC
   088C2F68: lw $a0,($s7)   ; $s7 = argv; $a0 = argv[0]
   ```

5. `sceUtilityInit` (0xBD1FC) с `$s0 = argv[0]`:
   - цикл из 6 вызовов `sceUtilityLoadModule(id)`; при ненулевом
     возврате — ЖУРНАЛИРОВАНИЕ ошибки через 0xBD6E4, не сравнение;
   - затем три сравнения ПРЕФИКСА `argv[0]`:

   ```
   strncmp(argv[0], "disc0:", 6)   ; vaddr строк 0x30B5D4/0x30B5DC/0x30B5E4
   strncmp(argv[0], "wlan0:", 6)
   strncmp(argv[0], "ms0:",   4)
   ```

   Игра по префиксу решает, где лежат её данные. `strncmp` — чистый
   (0x2D3764, разобран целиком), глобалей не пишет.

6. С пустым блоком: разбор пропущен, `argv[0] = NULL`, `strncmp`
   читает нулевой указатель — тот самый стабильный SIGSEGV.

## Причина

Мы запускали `module_start` с нулями — `guest_thread_enter(..., 0, 0, 0, ...)`.
На PSP ядро передаёт блок аргументов загрузки, для дисковой игры это
`"disc0:/PSP_GAME/SYSDIR/EBOOT.BIN\0"`. Всё остальное — следствие.

## Второй дефект: ошибка слотов в `sceKernelStartThread`

Старый код брал для точки входа `args[2]/args[3]`. Ядро PSP передаёт
точке входа `(arglen, argp) = ($a1, $a2)` вызова `StartThread`.
Измеренное доказательство ошибки: в кольце `StartThread` пришёл с
`a0=1, a1=0, a2=0, a3=0x00040000` — `a3` это застывший хвост от
предыдущего `CreateThread` (размер стека), а не аргумент. При пустых
аргументах ошибка была замаскирована: `a0=argp=0` случайно давал
«пропустить разбор» (`blez $a0`).

## Третий дефект: возврат `sceKernelLoadModule`

Гость проверяет результат командой `bgtz $v0` (0x088C13E0). Возврат 0 —
это «успех» в терминах нашей заглушки, но для гостя — ошибка: ветка
`"*** failed to sceKernelLoadModule %s[%X]\n"` (vaddr 0x30B5EC) зовёт
собственный `printf` гостя, которого у нас нет. Возврат обязан быть
ПОЛОЖИТЕЛЬНЫМ дескриптором.

## Что игра будет грузить (прогноз, проверяется пробом)

- Глобаль-селектор `0x327F0C` (начальное значение в `.data` — `-1`):
  единственный писатель — сам `F` (пишет `-1`). Никто в `.text` не
  пишет туда 0/1/2 — проверено полным проходом по парам HI16/LO16
  `.rel.text`. Значит ветка построения префиксов (`"disc0:/PSP_GAME/
  USRDIR/modules/"` / `"host0:./modules/"`) не выполняется ВООБЩЕ НИКОГДА,
  включая настоящую PSP.
- Вместо этого: `strcat(sp, *(0x327F00))`, где `*(0x327F00)` —
  указатель на `"psmf.prx"` (vaddr 0x30B57C). `strcat` по нулевому
  первому байту работает как `strcpy`: буфер `sp+0` — свежая, никогда
  не писаная часть стека потока, а стеки у нас статические и
  обнулены при старте. На PSP — то же самое с обнулённым стеком
  свежего потока.
- Итог: `sceKernelLoadModule("psmf.prx", 0, 0)` — ОТНОСИТЕЛЬНОЕ имя
  модуля. Ожидание на проб: слова
  `0x666D7370 0x7872702E 0x00000000...` ("psmf.prx").

## Правки (сборка `b6385de0`)

1. `module_start` получает `(sizeof("disc0:/PSP_GAME/SYSDIR/EBOOT.BIN"),
   указатель)` — блок в нашем `.rodata`, гость его только читает.
2. Точка входа потока получает `(args[1], args[2])` от `StartThread`;
   поля переименованы `argc/argv → args/argp`.
3. `sceKernelLoadModule` возвращает положительный дескриптор
   (`0x100 + счётчик`) и снимает путь (8 слов, только по проверенному
   адресу: образ гостя или стеки гостя) — печать в отчёте `lm*`.

## Ожидания на прогон (каждое проверяемо)

| поле | ожидание |
|---|---|
| `st_a1`, `ent_a0` | `0x21` (33 — длина блока с нулём) |
| `st_a2`, `ent_a1` | адрес `g_boot_args` в нашем образе |
| сбой на `0x08AD7788` | исчезает |
| `lm_count` | ≥1 |
| `lm0_w` | `2` (стек гостя) |
| `lm0r0..lm0r2` | `666D7370 7872702E 00000000` ("psmf.prx") |
| возврат `sceKernelLoadModule` в кольце | `0x101+` |

Если `lm0r*` покажет другое имя — разбор `strcat`-цепочки неверен, и
это будет видно сразу.

## Опровержения этого блока (записаны, чтобы не повторять)

1. **`R##`/`S##` в отчёте — НЕ регистры.** Это сырые слова кадра
   `ucontext` и `siginfo` по 20 слов. Регистры гостя — строки
   `G## имя=`. Из-за неверного прочтения я дважды приписал значения
   не тем регистрам: `0x2CAE009F` — это `$at` (не `$s4`), `0x28B6489C`
   — это `$v1` (не `$s0`). Настоящий `$s4` = `0x08B30000` (гость),
   настоящий `$s0` в кадре сбоя = `0`.
2. **«Протечка хостовых адресов в регистры гостя» — опровергнута.**
   Гостевые стеки — статические массивы в нашем `.bss`
   (`g_thread_stack`, `g_worker_stack`), и указатели гостя на его
   собственный стек — хостовские адреса ПО ПОСТРОЕНИЮ. Это не дефект
   нативного запуска, а его свойство. Регистр `$gp` действительно
   содержит хостовский мусор (`0x2CA24010`) — но `$gp`-относительных
   обращений в `.text` гостя всего 2 на весь образ, деклараций через
   `$gp` нет: безвредно.
3. **«В цикле 6× LoadModule есть сравнение» — ошибка чтения.** Там
   `jal 0xBD6E4` — журналирование ошибки при ненулевом возврате
   импорта. Сравнение с `"disc0:"` — ПОСЛЕ цикла, и упавшим было
   именно оно.
4. **Арифметика адресов в голове — снова ошибка:** `0x08A9C958 −
   0x08804000` = `0x298958`, а не `0x299958`; из-за этого был разобран
   вход СОСЕДНЕЙ функции. Правило «считать скриптом» нарушено вторым
   способом: не только адрес из файла, но и вычитание базы.
5. **Файл-адрес пары lui/lo после релокации НЕ равен загруженному
   смещению инструкции** (`0x7F0C` → `0xBF0C`), но ЭФФЕКТИВНЫЙ адрес
   совпадает с файловым из-за знакового расширения смещения: процессор
   складывает `0x8B30000 + (s16)0xBF0C = 0x08B2BF0C` = vaddr
   `0x327F0C`. Вывод «запись −1 и чтение попадают в одну глобаль»
   подтверждён только после этого пересчёта.

## Дополнение по результатам прогона (сборка `b6385de0`, 2026-10-14)

Прогон подтвердил цепочку загрузочных аргументов ЦЕЛИКОМ:

- `StartThread(1, a1=0x21, a2=<адрес буфера>)` — блок дошёл до потока;
- шесть `sceUtilityLoadModule` с теми же ID;
- три `sceKernelLoadModule` с возвратами `0x101/0x102/0x103`;
- `0x50F0C1EC` — это `sceKernelStartModule`: подтверждено строкой
  САМОГО ГОСТЯ `"*** failed to sceKernelStartModule %s[%X]"` (vaddr
  0x30B618). Наш возврат 0 принят как успех — ветка ошибки не печаталась.

### Опровержение собственного прогноза

**«Ветка disc0 мертва и на PSP» — НЕВЕРНО.** Снимок пути (`lm*`) показал
`"disc0:/PSP_GAME/USRDIR/modules/p…"` — дисковая ветка ВЫПОЛНИЛАСЬ,
то есть глобаль-селектор `0x327F0C` в момент чтения была 0, а не −1.
Писатель, ставящий 0, в парах HI16/LO16 `.rel.text` не находится —
значит, пишет через регистр-указатель, и такой поиск его видеть не
может. Прогноз про имя модуля подтвердился: загружаются `psmf.prx`,
`libpsmfplayer.prx`, `libfont.prx` (строки vaddr 0x30B57C/0x30B588/
0x30B59C).

Вывод-правило: **заключение «ветка недостижима», построенное на том,
что писатель не найден статическим сканом, — не доказательство.**
Скан по парам релокаций видит только прямые ссылки; записи через
указатели он не видит в принципе.

### Новый блокер: SIGILL на `cache`

Первый сбой после цепочки — `sig=4` (SIGILL, Reserved Instruction).
Заголовок сбоя читается так: `i0` — слово на `pc`, `i1` — слово на
`pc−4`, `r14` — регистр `0x14`=`$s4` (шестнадцатеричные номера).
Измерение:

```
0x237064: jal  импорт Kernel_Library
0x237070: cache 0x1B, 0($s1)   ← i1: НЕПОДДЕРЖИВАЕМАЯ cache-операция
0x237074: lw   …               ← i0: ядро дало pc = СЛЕДУЮЩУЮ инструкцию
```

`cache 0x1B` — легальный PSP-код (чистка кэша после загрузки модулей).
Во всём образе `cache`-инструкций РОВНО ОДНА (проверено по `.text` и
`.cplinit`), `pref` нет. Опкод `0x2E` (44 вхождения) — это `SWR`,
пара к `SWL`: ложная тревога, обычные инструкции.

Правка: `cache` → NOP при загрузке, ДО релокаций (после них слово могло
бы оказаться релоцированным указателем таблицы переходов в диапазоне
`0xBC000000..0xBFFFFFFF` — NOP испортил бы данные). Количество замен
печатается в отчёте как `cache_nops`; ожидаю 1.

Пропуск через обработчик сбоев отвергнут осознанно: семантика PC при
SIGILL на этом ядре — «после падающей» (измерено), обычное продвижение
срезало бы лишнюю инструкцию, а цикл чистки сжёг бы `FAULT_RECOVER_MAX`.

## Дополнение 2: прогон сборки `cebad126` (cache → NOP)

`cache_nops=1` — правка применилась, SIGILL ушёл. Следующий (и
единственный) сбой — в НАШЕМ коде, не в госте:

```
sig=000B addr=48BA0E80 pc=2CA07510   (i0=-: pc вне образа гостя)
```

### Зеркала памяти PSP — главное открытие прогона

Гость сдал GE-список по адресу `0x48BA0E80` — это его `.bss`
`0x08BA0E80` **с битом `0x40000000`**. У PSP одна память видна по
ЧЕТЫРЁМ адресам:

| зеркало | адрес | смысл |
|---|---|---|
| кэшируемое | `0x08xxxxxx` | единственное, что отображено у нас |
| без кэша | `0x48xxxxxx` | **через него гость сдаёт списки GE** |
| KSEG0 | `0x88xxxxxx` | |
| KSEG1 | `0xA8xxxxxx` | |

Аппаратный GE читает списки именно из безкэшевого зеркала — это
штатное поведение игры, а не ошибка. Наш `ge_walk` разыменовал сырой
адрес и упал; обработчик сбоев корректно опознал pc вне образа гостя
и завершил поток.

Правка: `list.cmds = args[0] & 0x3FFFFFFF` (нормализация всех зеркал),
`list_addr` остаётся сырым — пространство адресов обхода обязано
совпадать с тем, в котором гость пишет JUMP/CALL.

### Побочное измерение: первый список разобран

Первый `GE_EnQ=0x08B16D80` (список в `.rodata`, vaddr 0x312D80):
`stp=0xD4` (212 команд), `fin=1` (FINISH найден), **примитивов ноль**
(`p_spr=p_3d=p_oth=0`) — установочный список состояния, без рисования.
Второй список (в `.bss`) — ожидаемо с примитивами: его обход станет
первым измерением «2D или 3D» после правки зеркал.

Правка будет применена в сборке `fc333a23` (вывоз после возврата
плеера в сеть).

## Дополнение 3: зеркала отработали, SIGILL в HeapSystem (сборки `9032bd80`/`ab616f6e`)

Прогон `9032bd80` подтвердил двойное отображение ЦЕЛИКОМ:
`mirror=0x48804000`, каскад из 66 сбоев исчез (1 сбой за прогон),
`shell` выжил, отчёт дописан до конца. Записи гостя в зеркало теперь
работают нативно.

### Единственный сбой: SIGILL в инициализации кучи

`fault_pc=0x08AB9C7C` — ДВА прогона, ОДИН и тот же pc (воспроизводимо).
Контекст: `HeapSystem("HeapSystem", …, 0x4B30C0≈4.9 МБ)` — игра строит
свою кучу; выравнивание в ней делается `ins $vX,$vY,0,4` (SPECIAL3,
MIPS32R2) на `0x2B5AC0/0x2B5ACC` — в 0x1BC от pc. Во всём образе 271
`ins`, `ext`/`rdhwr` в тексте окна нет, FPU-команд вокруг точки нет.

**pc при SIGILL у этого ядра НЕ указывает на запрещённую инструкцию**
(измерено: на `cache` — pc-4; здесь — легальны pc, pc-4 и слот задержки).
Дозаявлено измерением: расширенное окно `w` `pc-0x200..pc+0x10`, ранний
маркер `SIGILL-SEEN`, сырой кадр 96 слов (до `sc_cause` — CP0 Cause с
ExcCode Reserved Instruction и битом BD).

### Эмуляция ins/ext в обработчике

`ins`/`ext` эмулируются по окну, поток продолжается с reported pc.
Обе операции идемпотентны, поэтому эмуляция уже исполненного слова
безвредна, а неисполнённого — правильна. Логика проверена на хосте:
identity-`ins`, реальный `ins`, `ext`, двойное применение — все OK.
Отчёт: `emul_ins=`. Если SIGILL не наш (в окне нет SPECIAL3) — поток
умирает, как прежде.

### Загадка пропавших строк сбоя (прогон `ab616f6e`)

`fault_sig=4/fault_pc` попали в финальный отчёт (значит, обработчик
их присвоил), но НИ ОДНОЙ строки сбоя в файле нет, при живом live-логе
до самого сбоя. Механизм не установлен; ранний маркер `SIGILL-SEEN`
(первая строка обработчика) даст ответ «дошёл ли обработчик до печати».

### Новый измеренный импорт: `sceGeEdramGetAddr`

`0xE47E40E4` = `sceGeEdramGetAddr` (установлено строкой гостя не было —
по tsv). Игра спрашивает адрес VRAM; наш возврат 0 разводит путь: в
этом прогоне GE-списки НЕ ставились в очередь. **VRAM (2 МиБ,
0x04000000 + зеркало 0x44000000) — следующий обязательный шаг** для
настоящего измерения «2D или 3D».

### Разошедшиеся пути прогонов 30 и 31

Прогон 30: GE-списки ×3 → SIGILL. Прогон 31: `sceGeEdramGetAddr`(=0)
→ без GE-списков → SIGILL на том же pc. Недетерминизм подтверждён —
вероятная причина прежняя: хостовый мусор в call-clobbered регистрах.

## Дополнение 4: пул 64-битных инструкций MIPS64 и точка продолжения (2026-10-15)

Прогон `34593d8a` дал полный разбор:

### Что сработало

- Маркер `SIGILL-SEEN` печатается — загадка «пропавших строк» закрыта
  (тогдашний файл, судя по всему, недокачан; версия с неполным fetch).
- Окно `w` показало виновника ВИЗУАЛЬНО: `w-6F=7C031804*`,
  `w-6C=7C021804*` — те самые два `ins` выравнивания кучи, ровно на
  `-0x6F` слов от pc (0x1BC).
- `emul_ins=2`: эмуляция применила оба, поток ПРОШЁЛ первый SIGILL.

### Что вскрылось

1. **`0x0202802C` = `dadd` (SPECIAL funct 0x2C, MIPS64).** objdump
   тулчейна опознал и семейство. Полный счёт по образу:
   `dadd` 40, `daddu` 86, `dmult/dmultu` 12, `dsrlv` 51. 64-битных
   сдвигов, `dmfc1/dmtc1`, `ldc1/sdc1` — НЕТ. PSP-тулчейн эмитит их,
   32-битный CPU плеера — нет.
2. **Ошибка точки продолжения в эмуляции**: после эмуляции `ins` поток

### Находка в СВОЕЙ верификации: число 0x0302 ломало хост-покрытие

### Метод дешифровки стэбов (повторяемый)

Адреса из таблицы NID:

### Находка 1: 64-битный возврат времени — КОРНЕВАЯ причина таймерного цикла

Таймерный поток на 0x088C17B0:

    88c17b0: jal GetSystemTimeWide
    88c17b8: move s3,v1          ← $v1 = старшие 32 бита
    ...
    88c17e0: jal GetSystemTimeWide
    88c17e8: move s1,v1          ← $v1 опять
    88c17f0: sltu a0,s0,s2       ← заём
    88c17f4: subu a1,s1,s3       ← 64-битное вычитание

Игра меряет кадр через полный u64 ($v0=low, $v1=high). В
$v1 после вызова оставался мусор из C-эпилога
`guest_import` → разность времени получалась случайной.
2.2 млн итераций цикла, который
должен закрываться за ~17 проходов — точный симптом.
Также `lui a0,0x4f80` (+4294967296.0) и div на 1e6 —
U64→float конвертация, дальше `helper(dt_sec)`.

Правка (сборка `0fce06d4`): в trampoline слот задержки
`jr ra` — вместо nop — `move $v1,zero`. Нулевая цена
(нет доп. байтов), чинит все u64-возвраты (v1 caller-
clobbered по o32: гость не имеет права опираться на
его сохранность; для u64-результатов 0 — правильное
старшее слово). Проверено в бинаре: sb zero/172(a0),
sb t2(=3)/174(a0).

Дополнительный выигрыш: пары структурных возвратов
v0/v1 теперь детерминированно равны нулям вместо
вылетевшего мусора из C-эпилога — то же поведение,
что у остальных заглушек (возврат 0).

### Находка 2: SleepThread-спин

## Дополнение 8: инцидент — вечный цикл в SleepThreadCB уронил shell (2026-10-19)

Сборка bc5641ea: SleepThreadCB сделан «вечным парком»
`for(;;) { cbk_deliver(); plat_sleep_ms(50); }` — по PSP-логике
ptnCallbackTh из него не возвращается. НА ПЛЕЕРЕ ЭТО ДАЛО
РЕСТАРТ-ЛУП ИНТЕРФЕЙСА.

Причина не в самой петле, а в её СВЯЗКЕ с host-жизнью плагина:
`guest_run_wait` выходит по 10-мин таймауту, пока поток ГОСТЯ
крутится в нашей библиотеке; хост после возврата делает
dlclose — библиотека выгружается ПОД ЖИВЫМ host-потоком, и
первый же вызов plat_sleep_ms уходит в освобождённую память.
Это ровно та грабля, что описана в guest_run_wait комментарием
про dlclose под работающим кодом — я прочитал её ПОСЛЕ
инцидента, а не до.

ПРАВИЛА, которые из этого следуют:
1. НИКАКАЯ заглушка HLE не имеет права не возвращаться:
   каждая обязана вернуться до того, как хост решит выгрузить
   библиотеку. «Вечный сон» возможен только через механизм,
   который хост знает (у нас такого нет — значит, возврат).
2. Перед каждой правкой цикла жизни потока — перечитать,
   как хост завершает плагин (wait/dlclose), и сверить с
   новым поведением.

Исправление (сборка 102805e6): SleepThreadCB → однократная
cbk_deliver() + 10-мс парк + возврат. Механика колбеков
(таблица CreateCallback uid→func/common, очередь notify от
UmdRegister/PowerRegister/devctl 0x2415821) сохранена
пассивно: уведомления копятся и исполняются при первом
SleepThreadCB. cb_fired= в отчёте покажет, дошла ли
доставка.

Пассивная база колбеков — подготовка к следующему шагу:
powerCB(0x088C28A8)/umdCB(0x088C2928)/msCB(0x088C2954)
расшифрованы, инициализация 0x327FF5/init-done = 0 в файле.
