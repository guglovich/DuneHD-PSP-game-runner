# Что гостевой код вызывает: точка входа и частота вызовов

Инструмент: `tools/import_callers.py`. Результаты для ULJS00042 (Magna Carta)
лежат в `docs/data/import-callers-ULJS00042.txt` и
`docs/data/import-stubs-ULJS00042.txt`.

## Зачем это

Импортов 147, а реализовывать все сразу не нужно и невозможно. Но важнее
обратное: гость начинает работу с вполне определённого набора вызовов, и если
не подменить их первыми, он упадёт сразу, и падение ничего не скажет. Поэтому
сначала смотрим, куда уходит управление из точки входа, и только потом пишем
обработчики.

## Точка входа

`entry` = `0x002B8EAC`, в гостевой памяти `0x08ABCEAC`. Дизасм (`objdump`
через `tools/prx_to_objdump.py`) со стабами, разрешёнными в имена:

```asm
002b8eac:  addiu sp,sp,-16
002b8eb0:  lui   a2,0x200
002b8eb8:  move  s1,a0            ; s1 = второй аргумент точки входа
002b8ebc:  ori   a0,a2,0x10       ; a0 = 0x0200010
002b8ec8:  jal   0x2ceed4          ; sceKernelSetCompiledSdkVersion
002b8ed0:  lui   a1,0x3
002b8ed4:  jal   0x2ceef4          ; NID 0xF77D77CB (SysMemForUser)
002b8ed8:  ori   a0,a1,0x303       ;   a0 = 0x0300303, a1 = 0x300000
...
002b8f38:  jal   0x2cef7c          ; sceKernelCreateThread
```

Три первых вызова — и это весь «стартовый минимум»:

| порядок | стаб | импорт | аргументы |
|---|---|---|---|
| 1 | `0x2CEED4` | `sceKernelSetCompiledSdkVersion` | `0x0200010` |
| 2 | `0x2CEEF4` | `SysMemForUser`, NID `0xF77D77CB` — **имя не найдено** | `0x300303`, `0x300000` |
| 3 | `0x2CEF7C` | `sceKernelCreateThread` | структура потока |

Практический смысл: **второй вызов при старте — один из четырёх
неопознанных NID.** Его придётся реализовать по поведению, а не по имени.
Второй аргумент `0x300000` — это ровно 3 МиБ, что для `SysMemForUser`
похоже на размер пула; первым идёт `0x0300303`, что указателем быть не может,
так что сигнатура, скорее всего, не `(имя, размер)`. Точное имя
устанавливается только сверкой с другими SDK или разбором использования.

Дальше из точки входа идёт стандартная инициализация: создание потока
главного цикла. Дальше работает уже созданный поток, и там нужен весь набор.

## Частота вызовов

Всего `jal` в исполняемых секциях — 48 692, из них в стабы импортов — 538,
при 147 различных импортах. **Вызваны все 147**, то есть «оставить
неиспользуемым» нечего, но порядок реализации определяется частотой.

| вызовов | импорт |
|---|---|
| 101 | `sceKernelSignalSema` |
| 51 | `sceKernelWaitSema` |
| 18 | `sceKernelCreateSema` |
| 14 | `sceKernelCpuResumeIntr` |
| 14 | `sceUmdWaitDriveStat` |
| 11 | `sceKernelDelayThread` |
| 10 | `sceKernelCpuSuspendIntr` |
| 10 | `sceKernelGetThreadCurrentPriority` |
| 9 | `sceKernelSetEventFlag` |
| 9 | `sceKernelDeleteSema` |
| 9 | `sceKernelCreateThread` |
| 9 | `sceKernelStartThread` |

Полный список — `docs/data/import-callers-ULJS00042.txt`.

Вывод по частоте: игра построена на семафорах. `SignalSema` и `WaitSema`
вместе дают 152 из 538 вызовов, то есть около 28 %. Значит первым делом
нужна **корректная синхронизация на семафорах**, а не графика: пока
`WaitSema` не блокирует поток по-настоящему, гостевой код не дойдёт до вывода
кадра, даже если `sceDisplay*` уже подменены.

Это отменяет очевидный на первый взгляд план «сначала видео».

## Нераспознанные NID

| NID | библиотека | вызовов | где вызывается |
|---|---|---|---|
| `0x4571CC64` | sceMpeg | 3 | в цикле декодирования |
| `0xF0A26395` | ModuleMgrForUser | 1 | инициализация модулей |
| `0xF77D77CB` | SysMemForUser | 1 | **второй вызов из точки входа** |
| `0xB011922F` | sceAudio | — | в справочнике SDK нет |

Первые три встречаются в конкретных местах кода, поэтому определяются
разбором аргументов и использования результата. `0xB011922F` — единственный,
чей NID не удалось найти и среди вызовов; вероятно, это экспорт с
нестандартным NID в самой игре.

## Как читается дизасм гостя

Гостевой код запускается по базе `0x08804000`, а адреса в образе — от нуля.
Поэтому при разборе адрес из дизасма надо прибавлять базу, иначе он не
совпадёт ни с чем наблюдаемым в отладчике:

```
адрес в дизасме  0x2B8EAC  ->  в гостевой памяти  0x08ABCEAC
стаб в дизасме  0x2CEED4  ->  в гостевой памяти  0x08AD32D4
```

`src/guest_load.c` печатает оба вида адресов, чтобы не путать.

## Чем игра на самом деле рисует

Установлено по полному списку 147 импортов и 538 вызовов
(`docs/data/import-callers-ULJS00042.txt`). Это меняет приоритеты.

### `sceGu*` — ноль вызовов

Игрового API 2D-рисования PSP (`sceGuDrawArrays`, `sceGuFillRectangle`,
`sceGuStartTessellation` и прочие) игра **не зовёт ни разу**. Значит путь
«переводить примитивы в команды GFX» для этой игры **не является рабочим**:
переводить нечего.

Это поправка к прежней оценке: работа над `FillRectangle` и `Surface` верна
сама по себе и полезна как инструмент, но на критическом пути для ULJS00042
она не стоит.

### Рисование идёт через GE и списки команд

| вызовов | функция |
|---|---|
| 7 | `sceGeEdramGetAddr` |
| 3 | `sceGeListEnQueue` |
| 2 | `sceGeListSync` |
| 2 | `sceGeDrawSync` |
| 2 | `sceGeListUpdateStallAddr` |
| 2 | `sceGeUnsetCallback` |
| 1 | `sceGeEdramGetSize`, `sceGeContinue`, `sceGeSetCallback`, `sceGeBreak`, `sceGeListEnQueueHead` |

Игра строит **списки команд GE** (display lists), отдаёт их `sceGeListEnQueue`
и ждёт `sceGeListSync`/`sceGeDrawSync`. Растеризацию выполняет геометрический
движок PSP.

**Собственного GE у нас нет.** Значит содержимое списков нужно либо
исполнять самим, либо переводить в команды GFX. Какой из опкодов списка игра
реально порождает — не установлено, и это главный открытый вопрос по
графике.

`sceGeEdramGetAddr` (7 вызовов) — игра берёт у движка кусок EDRAM под
временные данные.

### Смена кадра

| вызовов | функция |
|---|---|
| 6 | `sceDisplayWaitVblankStart` |
| 3 | `sceDisplaySetFrameBuf` |
| 1 | `sceDisplaySetMode`, `sceDisplayWaitVblank`, `sceDisplayGetVcount`, `sceDisplayGetFramePerSec` |

То есть на кадр игра зовет GE (список команд) и `sceDisplaySetFrameBuf`.
Собственного вывода примитивов нет.

### Критический путь по объёму вызовов

| доля | что |
|---|---|
| **170 из 538 = 31,6 %** | семафоры: `SignalSema` 101, `WaitSema` 51, `CreateSema` 18 |
| 18 | `sceKernelCreateThread` 9 + `sceKernelStartThread` 9 |
| 17 | флаги событий: `SetEventFlag` 9 + `WaitEventFlag` 8 |
| 0 | `sceKernelHeapAlloc` — **не вызывается ни разу** |

Про память: поверхность выделения крошечная — `sceKernelTryAllocateFpl` 2,
`sceKernelDeleteFpl` 1, `sceKernelFreeFpl` 1, `AllocPartitionMemory` 1,
`FreePartitionMemory` 1, `GetBlockHeadAddr` 1, `MaxFreeMemSize` 1. То есть
достаточно пула FPL и одного раздела, полноценный аллокатор кучи не нужен.

### Отдельная подсистема: MPEG

24 вызова `sceMpeg` — AVC (`sceMpegAvcDecode`, `sceMpegRegistStream`) и
ATRAC (`sceMpegAtracDecode`, `sceMpegGetAtracAu`). Похоже на вступительное
видео и/или фоновый звук. Вероятно, это необязательный путь, но надо
проверить, не блокирует ли он запуск.
