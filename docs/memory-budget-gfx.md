# Бюджет памяти: сколько стоит связка libdcchd + рантайм

Считаю сам, потому что от него зависит, помещается ли связка вообще.
Все числа — измеренные, источник указан. Неизвестные названы явно, а не
заменены нулями.

## Исходная точка

| величина | значение | источник |
|---|---|---|
| `MemFree` сейчас | **67 056 КБ = 65,5 МиБ** | живой плеер, `/proc/meminfo` |
| `Buffers` | 14 384 КБ = 14,1 МиБ | там же |
| `MemTotal` | ≈ 175 МиБ при `mem=192m` | там же |
| текст `shell` | 9 МиБ | разбор бинарника |

## Постоянные затраты нашей связки

| что | МиБ | примечание |
|---|---|---|
| цепочка `libdcchd` (69+13 библиотек) | **6,65** | измерено; `.bss` 0,74 из них. Не холодная плата: `libdcchd` и `libdirectfb` среди 81 `.so` у `shell` отсутствуют, то есть это реальная доплата |
| образ гостя, `mmap` | **4,61** | `0x08804000 .. 0x08CA0180` = 4 833 664 Б |
| стек гостя, резерв | **4,00** | выделяется 4 МиБ, реально коммитится ~1 МиБ |
| разделяемая страница состояния | **0,06** | 64 КиБ |
| **итого постоянно** | **≈ 15,3** | без кадрового буфера |

Пик при загрузке добавляет **5,35 МиБ** — расшифрованный образ (5 613 544 Б)
живёт в памяти, пока грузится. Одноразово, но вписывается в пик:

**пик ≈ 20,7 МиБ**, из которых 5,35 уходят после `guest_load`.

## Кадровый буфер — единственный крупный и пока неизвестный член

Разрешение экрана **с устройства не достаётся**:

* `/sys/class/graphics/` пуст, `fb0` там нет;
* `/proc/cmdline` содержит только `mem=192m`;
* `dmesg` про видеорежим молчит;
* `/dev/fb0..fb3` есть (char 29, миноры 0/32/64/96), но это не подсистема
  fbdev — нет ни sysfs, ни атрибутов.

Значит разрешение нужно взять из `shell` или из прошивки. От него зависит
расход, и он **доминирует во всём бюджете**:

| разрешение | один буфер, 32 бита | два буфера |
|---|---|---|
| 320×240 | 0,29 МиБ | 0,59 МиБ |
| 720×576 (PAL) | 1,58 МиБ | **3,16 МиБ** |
| 1280×720 | 3,52 МиБ | **7,03 МиБ** |
| 1920×1080 | 7,91 МиБ | **15,82 МиБ** |

## Сходится ли

Против 65,5 МиБ свободных, постоянные 15,3 МиБ оставляют **≈ 50 МиБ**.
Двойное буферизование укладывается при любом разрешении вплоть до 1080p:

| сценарий | всего | остаётся |
|---|---|---|
| 720p, два буфера | 15,3 + 7,0 = 22,3 МиБ | ≈ 43 МиБ |
| 1080p, два буфера | 15,3 + 15,8 = 31,1 МиБ | ≈ 34 МиБ |

**Вывод: по памяти связка помещается с запасом.** Это не тот ресурс, на
котором может закончиться дело.

## Память снята вопросом, а не размером

Измерено на живом плеере:

| | |
|---|---|
| MM1 всего | 203,9 МБ |
| MM1 занято | 121,4 МБ |
| **MM1 свободно** | **82,5 МБ** |
| MM0 свободно | **4,3 КБ из 101,9 МБ** — исчерпан |
| крупнейшая аллокация в MM1 | **94,2 МБ** |

**94,2 МБ = 12 полных кадров 1920×1080 по 32 бита** (7,91 МиБ каждый). По
размеру это видеоповерхность, а не OSD.

Отсюда **разрешение выхода — 1920×1080, 32 бита**. Это вывод **по размеру
аллокации, а не измерение**: отдельного измерения мы не делали, но
94 214 016 Б / 12 = 7 851 168 Б, что сходится с 1920×1080×4 = 8 294 400 Б с
точностью до выравнивания.

Два следствия:

1. **Видеопамять только в MM1**, MM0 исчерпан.
2. **Кадр 1080p — это 7,91 МиБ из MM1, а не из Linux RAM.** Всё, что касается
   поверхностей, идёт по пулу MM1 и в бюджет Linux RAM не входит. Строка
   «два буфера 15,8 МиБ» относится к MM1, где свободно 82,5 МБ, — то есть
   двойное буферирование там помещается с большим запасом.

Вывод прежний и усиленный: **вопрос никогда не был «сколько памяти нужно», а
«как получить дескриптор поверхности».**

## `/proc/pid/mem` на этом ядре не работает принципиально

`dd: /proc/<pid>/mem: No such process` — процесс жив, pid верный, права root,
узел существует. Причина: ядро `2.6.22.19-27-sigma` собрано **без
`CONFIG_PROC_PAGE_MONITOR`**: узел создаётся, но не работает.

Это задним числом объясняет и прошлый «контрольный провал» чтения по
`0x400000` — дело было **не в расхождении ELF**, а в этом.

**Следствие, постоянное:** снять `surface_t` из работающего `shell` нельзя
вообще. Вопрос «какая поверхность свободна» через память процесса не
закрывается и, вероятно, не закроется.

## Поверхность картинки — НЕ из Linux RAM

Это перекрывает расчёт выше, поэтому вынесено отдельно и явно.

`dcchd_mruamem_alloc` работает с **пулами MM0/MM1** через
`em86_alloc_mapped_memory`, а не с кучей Linux:

```c
if (mgr->field_27880 == 0) goto fail;
if (*A < size) goto next_pool;
if (*B < size) goto next_pool;
p = em86_alloc_mapped_memory(mgr->field_27888, size, 0);
```

* Восемь каскадных сравнений лимитов, `sltu` — рукописная куча пулов
  разного размера, а не один `malloc`.
* В пуле 13 градаций по степеням двойки, `2048 << i`, до `2048 · 2¹²` = 8 МБ.
  Этот же ряд объясняет литерал `0x8000` в `gfx_open`.
* Смещение `27880` = `0x6CF0` — **за пределами `.bss` самой `libdcchd.so`**
  (а `.bss` у неё всего 3408 Б). Значит менеджер пулов — объект из другой
  библиотеки, и пулы живут там.

Формулировка, которую надо использовать во всех документах:

| что | откуда | уверенность |
|---|---|---|
| буфер команд | `realloc`, куча Linux | **подтверждено** |
| поверхность картинки | `dcchd_mruamem_alloc` → пулы MM0/MM1 | **подтверждено** |

Следствия, важные для порядка работы:

1. **`dcchd_mruamem_alloc` из своего процесса звать нельзя.** Он работает с
   чужим менеджером, состояние которого лежит в памяти плеера; рассинхрон его
   сломает. Это не «нежелательно», а нерабочее.
2. **Поверхность надо получать, а не создавать.** Единственная заведомо
   валидная опора — `buffer_addr` (`0x00DA5340`) из работающего `shell`, но он
   принадлежит `shell`, и писать в него нельзя.
3. **И тут развилка смыкается с тем, о чём мы уже знали:** `.bss` нельзя
   читать по адресам ELF на живом процессе, а координаты OSD лежат именно там.
   Значит «взять адрес из работающего `shell`» технически недоступно из
   постороннего процесса — и это возвращает нас ровно туда, где мы и стоим:
   **рантайм должен работать внутри `shell`**.

Итог по бюджету: смета выше остаётся верной для **связки** (буфер команд,
образ, стек), но **строка «свой кадровый буфер 0,6–15,8 МиБ» из неё выпадает**:
своей поверхности у нас не будет.

## Оговорки, без которых вывод обманчив

1. **`MemFree` колеблется.** Значение снято в один момент; во время работы
   интерфейса и после `dlopen` оно будет меньше. Проверять надо после
   загрузки, а не до.
2. **Отдельный процесс против `shell`.** Сейчас рантайм — отдельный процесс,
   то есть платит ещё и за собственные страницы. При переезде внутрь `shell`
   эти страницы исчезают, но появляется риск, что `shell` уже занял что-то;
   суммарная память та же.
3. **`libdcchd` тянет около 70 библиотек.** VM растёт на 6,65 МиБ сразу, RSS —
   на меньшую величину. Мы считали по отображённому, то есть по верхней оценке.
4. **Стек гостя 4 МиБ — резерв, а не коммит.** Реально страницы появляются по
   мере использования.
5. **Собственные буферы DSP** (MM0, 65 МиБ видео) в этот бюджет **не входят**:
   это резервы железа, и мы к ним не обращаемся.

## Что нужно измерить дальше

1. **Разрешение и формат OSD** — из `shell` или прошивки, с устройства не
   берётся. Определяет, сколько занимает кадр, который мы **получим**, а не
   создадим.
2. **`MemFree` сразу после `dlopen` цепочки `libdcchd`** — верхняя оценка
   сейчас посчитана по отображённой памяти.
3. **Фактический RSS нашей библиотеки внутри `shell`**, а не только VM.
4. **Сколько стоит получение поверхности, если это вызов обратно в `shell`.**
   Вероятно ноль — просто передать указатель, — но это неизвестно, и от этого
   зависит, укладываемся ли мы в бюджет вообще.
