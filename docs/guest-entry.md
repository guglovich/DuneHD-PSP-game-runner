## Раскладка ucontext измерена пробой

`tests/uctx_layout.c` — отдельная проба. Гостевой код загружает в регистры
заранее известные значения, выполняет `break`, обработчик просматривает
контекст и отмечает смещения, где значения встретились. Каждое значение
уникально, поэтому поле определяется фактом.

Результат на плеере:

| поле | смещение в байтах | индекс `gregs[]` |
|---|---|---|
| PC | **32** | — (в `gregs[]` его нет) |
| `$v0` | 56 | 2 |
| `$a0` | 72 | 4 |
| `$a1` | 80 | 5 |
| `$a2` | 88 | 6 |
| `$a3` | 96 | 7 |
| `$gp` | 264 | 28 |

То есть `gregs[i]` = 40 + 8·i: **шаг 8 байт, начало 40**. Согласованность
проверяется по `$gp`: 40 + 8·28 = 264, и проба нашла его именно там.

Две ошибки, обе пришедшие из-за этих смещений:

* **смещения обязаны быть в байтах.** Первая версия читала
  `((u32 *)ctx)[CTX_A0]`, то есть 4·i байт, и печатала `0x00000002` во всех
  аргументах вместо значений;
* **прежнее утверждение «`gregs[2]` — это не `$v0`» было неверным.** Измерение
  показало, что `gregs[2]` — как раз `$v0`. Прежний вывод сделан был не из
  измерения, а из рассуждения, и рассуждение ошиблось.

**Раскладку не берут из заголовка musl** — там она другая, и перебор по
`gregs[]` даёт нули.

Проба же показала и грабли: обработчик в ней вызывает
`__builtin___clear_cache`, то есть libc, — и подмена ловушки не видна кэшу
команд, ловушка срабатывает снова (683 282 раза до аварийного выхода).
В рантайме это давным-давно исправлено прямым `syscall`, здесь — нет.
Второй граблей пробы был недопустимый `$sp` в гостевом коде: обработчик
работает на прерванном стеке и падал раньше, чем что-либо измерил.

## Потоки: реализованы, и видно, где игра падает

`sceKernelCreateThread` и `sceKernelStartThread` реализованы. Настоящего
планировщика нет: обработчик ловушки запоминает функцию потока, а запускает её
родитель после возврата гостя из точки входа — отдельным потомком, чтобы сам
остаться целым (`guest_enter` в C не возвращается).

Смещения `$a0`..`$a3` использованы не по номерам, а по смыслу. Замер на
`CreateThread` показал шестиаргументный вызов:

```
$a0 = 0x08ACBBC8   строка имени в .rodata гостя
$a1 = 0x08ABCF68   адрес в тексте гостя — функция потока
$a2 = 0x00000020   32
$a3 = 0x00019000   102400 — размер стека
```

Ни один аргумент, кроме `$a1`, на код не похож, поэтому функция потока берётся
из `$a1`. Формально сигнатура `sceKernelCreateThread` семиаргументная, но
фактические данные однозначны; расхождение отмечено, а не достроено догадкой.

**Сквозная передача возврата подтверждена:** `CreateThread` вернул 1, и
`StartThread` получил в `$a0` ровно `0x00000001`.

Поток пошёл и упал. Полная картина запуска:

```
Гость ВЕРНУЛСЯ из точки входа, код 0
Поток гостя: функция 0x08ABCF68, запуск запрошен
СБОЙ в потоке гостя: сигнал 11, si_addr 0x00000000
      PC (+32)   = 0x08AA6914  — в госте
      вызовов импортов: 7
```

Семь вызовов, то есть поток исполнился и дошёл дальше точки входа:

| # | NID | функция | реализация |
|---|---|---|---|
| 1 | `0x7591C7DB` | `sceKernelSetCompiledSdkVersion` | есть |
| 2 | `0xF77D77CB` | `SysMemUserForUser` | есть |
| 3 | `0x446D8DE6` | `sceKernelCreateThread` | **есть** |
| 4 | `0xF475845D` | `sceKernelStartThread` | **есть** |
| 5 | `0xD8B73127` | `sceKernelGetModuleIdByAddress` | нет |
| 6 | `0x092968F4` | `sceKernelCpuSuspendIntr` | нет |
| 7 | `0x5F10D406` | `sceKernelCpuResumeIntr` | нет |

Падение — `SIGSEGV` с `si_addr = 0`, то есть прыжок по нулевому адресу.
По дизасму расшифрованного образа (`tmp/EBOOT.asm.BIN`, смещение
`0x08AA6914 - 0x08804000 = 0x2A2914`) это:

```
2a2908:  1340003a   beqz   $k0,0x2a29f4
2a290c:  afb00000   sw     $s0,0($sp)
2a2910:  8f500004   lw     $s0,4($k0)     ← PC сбоя = 0x2A2914
2a2914:  52000038   beqzl  $s0,0x2a29f8

```

Похоже на обход связного списка через `$k0`/`$s0` — типичный код ядерных
структур PSP. Следующий предмет — разобрать, что стоит за `0x2A29F8` и откуда
берётся нулевой адрес; `GetModuleIdByAddress` с возвратом 0 здесь кандидат,
но это гипотеза, а не измерение.


## Раскладка ucontext — полная таблица (измерена)

`tests/uctx_layout.c` помечает метки во всех регистрах и находит их смещения в
кадре. На 24 метки найдены 22; смещения в байтах:

| регистр | смещение | индекс `gregs[]` |
|---|---|---|
| PC | **32** | — |
| `$at` | 48 | 1 |
| `$v0` | 56 | 2 |
| `$v1` | 64 | 3 |
| `$a0` | 72 | 4 |
| `$a1` | 80 | 5 |
| `$a2` | 88 | 6 |
| `$a3` | 96 | 7 |
| `$s0`..`$s7` | 168..224 | 16..23 |
| `$t8` | 232 | 24 |
| `$t9` | 240 | 25 |
| **`$k0`** | **нет** | — |
| **`$k1`** | **нет** | — |
| `$gp` | 264 | 28 |
| `$sp` | 272 | 29 |
| `$fp` | 280 | 30 |
| `$ra` | 288 | 31 |

Итого `gregs[i]` = 40 + 8·i, `i` = 1..31, **`$k0` и `$k1` в кадре отсутствуют**.

Это ключевой факт для падения гостя: гостевой код по адресу `0x08AA6910`
начинается с `beqz $k0` и читает `lw $s0, 4($k0)` — то есть **`$k0` у него
входной параметр**. Если musl при возврате из обработчика `$k0` не
восстанавливает, то после КАЖДОГО вызова импорта гость теряет `$k0`.

**Прямая проверка выживания `$k0`/`$k1` закрыта: они затираются.**

```
$ кода вокруг ловушки : 241A100A 241B100B 00000000 00000000 AC800108
ловушек             : 2      подмена : да      потомок вышел с кодом 42
$k0 было 0x0000100A, после 0x2ADEBCD0  ЗАТЁРТ
$k1 было 0x0000100B, после 0x8BBF7FE0  ЗАТЁРТ
```

Гость записал значения сам, в разделяемую страницу, после ловушки. Оба
регистра после возврата из обработчика содержат **адреса хостового кода**.

Это и есть причина падения: гостевой код по адресу `0x08AA6910` начинается с
`beqz $k0` и читает `lw $s0, 4($k0)` — `$k0` у него входной параметр. После
каждого вызова импорта гость получает вместо него хостовый адрес, уходит не
в ту ветку и в итоге приходит к прыжку по нулю.

**Механизм ясен:** раз `$k0`/`$k1` не лежат в кадре, их не восстанавливает ни
ядро, ни musl, и после обработчика в них остаётся то, чем musl пользовался как
временным. Восстановить их из C нельзя — они не адресуемы.

### Путь, который это снимает

Ловушка на `break` здесь принципиально ограничена: она проходит через
сигнальный механизм, а тот теряет два регистра, которые гость использует.
Значит рабочий вариант — **не сигнал, а трамплин**.

Стабы остаются `j` на трамплин (8 байт, как сейчас), трамплин живёт внутри
отображения гостя. Адрес хостской функции в трамплине **записывается из C при
загрузке**: `lui`/`ori` абсолютным 32-битным значением, плюс `lui`/`ori` для
`$gp`. Это обходится без `R_MIPS_HI16`, который в shared-объекте не линкуется,
потому что релокации не нужна вовсе — значение подставляется числом.

Что это даёт: ни musl, ни сигнальный механизм в цепочке не участвуют, значит
`$k0`, `$k1`, `$t9` и `$gp` не портятся ни при каких обстоятельствах, и
сбрасывать кэш команд внутри обработчика больше не нужно.

Цена: своя раскладка аргументов вызова и своя логика сохранения регистров
внутри трамплина.

## Смещение 32 — это PC только для SIGTRAP

Для SIGSEGV поле по смещению 32 достоверным не является: в сбое потока там
оказался `beql`, который не может вызвать SIGSEGV (проверено по загруженной
памяти). Отдельная фаза пробы с `jalr` по нулевому адресу до сих пор не даёт
кадра: обработчик SIGSEGV не вызывается вовсе, потомок гибнет по `SIGALRM`,
а чтение данных по адресу 0 на этом ядре SIGSEGV не даёт вовсе.

**Практический вывод:** диагностика падения гостя по PC не работает, и
локализовать сбой по ней нельзя. Нужен другой способ.

## Выводы по последним прогонам: трамплин верён, а «инструкция» была мусором

Плеер был выключен, поэтому проверки шли локально. Обе оказались нужными.

### 1. Знак в `addiu` при вычислении `$gp` — ошибка на 0x10000

`gp_value()` вычислял `_gp` как `(hi << 16) + lo + fn`, где `lo` брался без
знакового расширения. `addiu` расширяет непосредственный операнд **знаком**, и
при `lo > 0x8000` адрес уезжал на `0x10000`, то есть `$gp` указывал не в GOT.
Проверено измерением, что и как это ломало:

| | вычисленный `_gp` | `_gp − 32728` | там на самом деле |
|---|---|---|---|
| без знака | `0x28010` | `0x20038` | `.got + 0x18` |
| нужно | `0x27FF8` | `0x20020` | начало `.got` |

`_gp` = `0x28010` и есть значение символа `_gp` из таблицы символов, а
`_gp − 0x7FF0 = 0x20020` — ровно начало `.got`, то есть стандартное смещение
MIPS. Ошибка исправлена, гейт — `tools/gpcheck.c`.

Про `lo` реального пролога (`0x4CFC` = 19708 < 0x8000) знак не меняет
результата, поэтому гейт проверяет знаковое расширение **на синтетическом
`lo = 0x9000` отдельно** от пролога. Первая версия гейта сравнивала две
реализации друг с другом и на сломанной формуле проходила — то есть не ловила
ровно тот дефект, ради которого написана. Проверено на намеренно испорченной
копии: исправная даёт код 0, испорченная — код 1.

### 2. Трамплин собирается верно — проверено дизасмом

`guest_build_import_trampoline` тестами не покрывался: `tests/guest_load_test.c`
проверял **старую** форму (`lui/jr/addiu`, 3 слова), а на плеере работает
новая — 37 слов. Дыра была ровно там, где произошло падение.

`tests/tramp_dump.c` собирает те же байты на хосте и отдаёт их `objdump`.
Дизасм всех 37 слов верен: все `sw`/`lw` идут через `$sp`, стаб — `j` +
`nop`, `lui/ori` собирают адрес функции и `$gp`, вызов — `jalr $t9`, возврат —
`jr $ra`. **Значит SIGILL не в трамплине**, и искать надо было не в нём.

### 3. Диагностика показывала данные вместо кода

Отчёт по SIGILL 4 содержал «инструкцию» `64615F69 30207264 38302578`. Это
ASCII `i_ad`, `0 rd`, `80(x` — **часть строки формата** `"i_addr 0x%08X\n"` из
`.rodata` нашего образа (файловое смещение `0x13318`).

Механика: `guest_fault` брал адрес из поля +32 и читал по нему 4 слова. Для
SIGTRAP это PC, для SIGSEGV/SIGILL — нет. При SIGILL поле указало внутрь
`.rodata`, проверка «в нашем образе» **прошла**, и обработчик вычитал четыре
байта текста, пометив их как инструкцию. Отсюда вывод «трамплин исполняет
мусор» был бы неверен — читать было нечего.

Исправлено: слова инструкции читаются **только при `sig == SIGTRAP`**, а в
отчёте поле +32 печатается с пометкой `НЕ PC: достоверно только для SIGTRAP`
и больше не подаётся как адрес сбоя.

**Обобщение правила:** поле контекста, измеренное для одного сигнала, нельзя
использовать для другого даже с проверкой «адрес похож на наш». Проверка
проходила, а значение всё равно было чужим. Достоверность поля определяется
сигналом, и это обязано быть в коде, а не в догадке при разборе.

## Трамплин возвращается — падение в гостевом коде (метка возврата)

Прежде сбой локализовать нельзя было, потому что не было известно даже, где он:
внутри нашего трамплина или уже в коде гостя. Регистры гостя после вызова
импорта и перед ним почти одинаковы, а PC не извлекается.

Решается тривиально: трамплин непосредственно перед `jr $ra` записывает свой
индекс в разделяемую страницу (`tramp_done`). Значение в странице — индекс
последнего импорта, чей трамплин **вернулся в гостя**.

Замер на плеере: `трамплин вернулся по импорту: 101` при 5 обработанных вызовах.
То есть падение происходит **после** возврата трамплина, в коде гостя.

## Карта мест вызова: гость не выходит за пределы образа

Трамплин передаёт обработчику и `$ra` — это адрес возврата, то есть точное
место вызова импорта в коде гостя. Все семь мест вызова лежат внутри `.text`
(`0x08ABCED0`, `0x08ABCEDC`, `0x08ABCF40`, `0x08ABCF50` и далее), образ гостя
`0x08804000..0x08CA0180`.

Значит гипотеза «гость исполняет код вне своего образа» на местах вызова **не
подтверждается**: все стабы зовутся из нормального кода.

## Данные гостя теперь неисполняемы — и по дороге найден баг в загрузчике

Отображение гостя одно и помещается в `RWX`, а кроме кода там лежат `.data`
(730 КБ) и `.bss`. На настоящей PSP страницы кода и данных разделены, и это
различие могло быть причиной «необъяснимых» значений `$k0`. Теперь с данных
право исполнения снимается через `mprotect`, а в отчёте печатается, сработала
ли защита и по какому смещению (`data_off` = `0x002CFCC8`).

По дороге выяснилось, что путь «защита от подмены адреса» в `map_guest` был
**не просто бесполезен, а опасен**:

```c
#ifdef MAP_FIXED_NOREPLACE
    p = mmap(want, ..., MAP_FIXED_NOREPLACE, ...);
```

Флаг определён в заголовках musl, но ядро `2.6.22` его не знает и **игнорирует**.
То есть вместо «не трогать чужое отображение» получалось поведение `MAP_FIXED` —
с подменой чужого отображения. И этот же путь делал ранний `return true`,
из-за чего `mprotect` не вызывался вовсе. Путь удалён.

Ошибка проявилась с опозданием и как «загадочное» НЕ сработавшее свойство, а не
как опасный `mmap`. **Общее правило: `#ifdef` по флагу из заголовков libc не
проверяет, знает ли флаг ядро; на старом ядре это молча меняет смысл вызова.**

## Подделка структуры `GetModuleIdByAddress` не причина — доказано A/B

Гипотеза была: гость получает от `GetModuleIdByAddress` указатель на 16 байт
нулей, читает из них указатель на функцию и зовёт ноль. Проверено сравнением
прогонов с переключателем `NO_THREAD_INFO`:

| | PC | si_addr | вызовов | трамплин вернулся |
|---|---|---|---|---|
| подделка включена | `0x00000000` | 0 | 5 | импорт 101 |
| подделка выключена | `0x00000000` | 0 | 5 | импорт 101 |

**Прогоны неразличимы, значит подделка не причина.** Её оставили выключенной по
умолчанию для чистоты: она не даёт пользы.

## Состояние потока гостя на момент сбоя (замер)

```
Поток гостя: функция 0x08ABCF40
            стек потока 0x2AEDC000, вершина 0x2AFDC000
PC (+0xF0)  = 0x00000000
sp          = 0x2AFDC010
ra          = 0x00000000
цепочка вызовов: пусто
трамплин вернулся по импорту: 101
```

`$sp` на 16 байт **выше** вершины стека, то есть пролог функции потока
(`addiu $sp,$sp,-1008`) **не выполнялся**. Значит прыжок на ноль произошёл до
первой инструкции функции потока либо на ней самой.

Проход по стеку (512 слов от `$sp`) не нашёл ни одного адреса образа гостя —
сохранённых адресов возврата в стеке нет, что согласуется с тем, что
функция не успела ничего положить.

## Что осталось нерешённым

Падение потока гостя — прыжок по нулевому указателю (`PC = 0`, `si_addr = 0`,
`$ra` = 0). Значит гость зовёт функцию, адрес которой мы отдали нулём. Адрес
инструкции установить нельзя: поле PC измерено (`+0xF0`, четыре вида сбоя), но
кадр гостя не совпадает ни с одним измеренным случаем — расхождение не
объяснено.

Прогоны недетерминированы (5 или 7 вызовов), и причина, по всем признакам,
`$k0`: он меняется между вызовами, хотя проверенным инструментом не найдено ни
одной инструкции `.text`, которая его пишет.

## Уточнение к измерению: `+0xF0` верен для ЧЕТЫРЁХ видов сбоя

Проба `tests/uctx_segv.c` расширена режимом `fetch0` — выборка команды **по
адресу 0**, то есть ровно то, что делает гостевой поток. Это отдельный случай:
в трёх предыдущих сбой происходил по непустому адресу.

| вид сбоя | `+0x20` | `+0x40` | `+0xF0` |
|---|---|---|---|
| чтение | PC | PC | PC |
| запись | PC | PC | PC |
| выборка команды, адрес высокий | содержимое регистра | PC | PC |
| **выборка команды, адрес 0** | **0** | **0** | **PC** |

`+0xF0` верен во всех четырёх — вывод устойчив.

### Но случай гостя не совпадает ни с одним

У гостя при сбое читается:

```
PC (+0xF0) = 0x00000000
+0x20       = 0x08ABD01C      <- код гостя
+0x40       = 0x2AACC000      <- диапазон хоста
si_addr     = 0x00000000
```

В пробе `fetch0` при `si_addr` = 0 поля `+0x20` и `+0x40` **обнуляются**, а
`+0xF0` содержит PC. У гостя `+0x20` = `0x08ABD01C`, то есть не ноль. Значит
сбой гостя — **не** выборка команды по адресу 0, и `PC = 0` в его кадре не
объясняется ни одним из измеренных случаев.

**Это не решено.** Расхождение между кадром гостя и кадром пробы не установлено.
Наиболее вероятное, но НЕ проверенное объяснение: гость падает в потомке после
`fork`, на стеке, выделенном `mmap` у родителя, и это не воспроизведено пробой.
Проверка тривиальна — добавить в пробу `fork` и повторить — но она не сделана.

До тех пор утверждать «PC гостя равен 0» нельзя с той же строгостью, с какой
измерено `+0xF0`. Прежний вывод сессии («гость прыгает по нулевому указателю»),
по этому основанию **снят**.

## РАЗБЛАЖЕНО: поле PC в ucontext — `+0xF0`, а `+32` годилось только для сбоя по данным

Прежнее утверждение «смещение 32 непригодно для SIGSEGV» было **неполным**, и
из него вырос лишний вывод, будто локализовать падение нечем вовсе.

`tests/uctx_segv.c` — проба, которая измеряет положение PC отдельно для двух
видов сбоя. Адрес инструкции известен заранее: она помечена глобальной меткой
в отдельном ассемблерном фрагменте, и её адрес передаётся обработчику **до**
сбой. Сбой по данным вызывается чтением со страницы, снятой `munmap` (чтение по
адресу 0 на этом ядре SIGSEGV не даёт).

Результат на плеере, 4 прогона, стабильно:

| вид сбоя | `+0x20` | `+0x40` | `+0xF0` |
|---|---|---|---|
| по данным | **PC** | PC | **PC** |
| по выборке команды | **содержимое регистра** | **PC** | **PC** |

**`+0xF0` — единственное поле, верное в обоих случаях.**

Отсюда всё объясняется: рантайм читал `+0x20`, то есть верное поле только для
сбоя по данным. При падении в гостевом потоке сбой оказывался **по выборке
команды**, и на месте `+0x20` лежало содержимое регистра — отсюда
нестыкуемые `0x08ABD018`, `0x08ABD01C`, `0x08ABD014` при одном и том же
падении. Значение менялось не потому, что PC «ненадёжен», а потому что
читалось не то поле.

Первая версия пробы искала в кадре **адрес снятой страницы** вместо адреса
инструкции — это ошибка, и с ней поиск совпадал со всем подряд. Вторая
версия задавала ожидаемый PC только для режима fetch, и в режиме data он
оставался нулём, а ноль совпадал с полями кадра всюду.

### Что сразу изменилось: падение локализовано

После чтения PC по `+0xF0` сбой потока гостя читается так:

```
PC (+0xF0)  = 0x00000000
si_addr     = 0x00000000
ra          = 0x08ABD010
```

**PC = 0** — это не запись в память, а **выборка команды по адресу 0**: гость
прыгнул по нулевому указателю. Это опровергает прежнюю версию о записи
`sw $s5,4($k0)`: та инструкция не была достигнута, и весь разбор вокруг неё
(включая подмену `$k0` при запуске потока) относился к недостижимому коду.

## Гость не пишет в `$k0`/`$k1` НИ ОДНОЙ инструкцией — инструмент проверен

Инструмент `tools/find_k0.py` ищет инструкции, пишущие в `$k0`/`$k1`, по обеим
исполняемым секциям: `.text` (2 944 532 Б) и `.sceStub.text` (1176 Б).
Результат: **0**.

Только теперь этому можно верить, потому что инструмент проверен:

* первая версия определяла «пишет ли» по вхождению в фиксированный список
  (SPECIAL с `rd` в `addu/or/and` плюс `addiu/lui/lw/lb`). Она пропускала
  `sll rd,rs,0` (`move`), `movz`, `movn` — а это и есть обычные способы;
* `pref` (op `0x2F`) в список попадал, хотя ничего не пишет: единственное
  найденное вхождение оказалось ложным;
* отбор секций был **по имени** (`.text`), а не по флагу `SHF_EXECINSTR`, и
  `.sceStub.text` (флаги `0x6`) проходила мимо;
* самопроверка сначала была негодной: проверяли на `psp-hle`, где к тому
  моменту подмена `$k0` в `guest_enter` уже была откачена — проверять было
  нечего, и инструмент «проходил» на заведомо годном входе.

Настоящая проверка — `tests/find_k0_test.c`: программа, где каждая форма записи
перечислена явно (8 форм), плюс 3 контрольные, которые писать не должны
(`sll $0`, `pref`, `sw` в память). Собранная и прогнанная: найдены все 8 форм,
ложных срабатываний нет. Только после этого результат «0 по гостю» признан.

## Нерешённое противоречие: `$k0` меняется, хотя писать его некому

Три факта, каждый измерен:

1. В коде гостя нет инструкций, пишущих `$k0`/`$k1` — проверено проверенным
   инструментом по обеим исполняемым секциям.
2. Трамплин на плеере сохраняет и восстанавливает `$k0` — проверено выгрузкой
   байтов: `sw $k0,48(sp)` в начале, `lw $k0,48(sp)` после `jalr`.
3. При этом `$k0` **меняется между вызовами импортов внутри одного процесса**:
   pid 1341 — `0x001F501E`, `0x001F501E`, `0x001FF918`, `0x001FF918`;
   pid 1342 — `0x001E1A1A`, `0x001E1A1A`, `0x001F4C1E`.

Добавлена проба: `guest_enter` перед прыжком ставит `$k0 = 0x5A5A5A5A`
(`li $26,0x5A5A ; ori $26,$26,0x5A5A`, проверено дизасмом собранного бинарника).
В логе `0x5A5A5A5A` **не появилось ни разу** — вместо него `0x001Exxxx`.

Значит `$k0` меняет кто-то, кто не является ни кодом гостя из файла, ни нашим
трамплином. Кто — **не установлено**. Проба убрана: она была экспериментом, а
не исправлением, и оставлять в `guest_enter` безосновательную константу нельзя.

Значения `0x001Exxxx` устойчиво лежат в узкой полосе и меняются через два
вызова. Это признаки, которые стоит проверить следующими: не выполняется ли гостем
код, полученный откуда-то ещё (распакованный в кучу), и не попадает ли
управление в область за последним трамплином.

## `$k0` — рабочий регистр гостя, измерено пробой через трамплин

Прочитать `$k0` из отчёта о сбое нельзя (его нет в кадре сигнала), поэтому он
передан в обработчик **трамплином**: `move $a2,$k0` перед `jalr`. Так он виден
на каждом вызове импорта.

Результат на плеере:

| вызов | NID | `$k0` в момент вызова |
|---|---|---|
| 1 | `0x7591C7DB` SetCompiledSdkVersion | `0x001DB51E` |
| 3 | `0x446D8DE6` CreateThread | `0x001EDE18` |
| 5 | `0xD8B73127` GetModuleIdByAddress | `0x001F9F1A` |
| 6 | `0x092968F4` CpuSuspendIntr | `0x001F9F1A` |
| 7 | `0x5F10D406` CpuResumeIntr | `0x001DB11E` |

Значения меняются от вызова к вызову и лежат вне образа гостя
(`0x08804000..0x08CA0180`). То есть **`$k0` у гостя — обычный рабочий регистр**,
который он перезаписывает сам, а не входной параметр от «ядра».

Из этого следуют два отозванных вывода:

1. **«$k0 = 0, значит запись по нулевому указателю»** — неверен: значение бралось
   из разрыва в раскладке, а не из регистра.
2. **«Наполнять `$k0` должен запуск потока»** — тоже неверен: подмена была
   поставлена, `$k0` получал настоящий адрес, и после этого `si_addr` изменился
   с `0x04` на `0x00` (3 прогона из 3 стабильно), то есть запись
   `sw s5,4($k0)` перестала падать — но гость затирает `$k0` раньше, и подмена
   ничего не даёт. **Откат выполнен.**

Вывод, который остаётся твёрдым и получен методом исключения, а не из отчёта:
между возвратом из `CpuResumeIntr` (`$ra` = `0x08ABD010`, смещение +288 это `$ra`,
измерено) и сбоем остаются ровно `bltz v0`, `nop`, `sw s5,4($k0)`. Из `bltz` и
`nop` SIGSEGV получиться не может — виновна эта запись. Но в какую инструкцию
сбой уходит после неё, установить нечем.

## ОТЗЫВ: «$k0 = 0, значит запись по нулевому указателю» — вывод неверен

Разбор дал `0x08ABD018  sw s5,4(k0)`, а отчёт о сбое показывал `k0 = 0`, и из
этого сделан вывод о записи по нулевому указателю.

**Вывод построен на несуществующем поле.** Проба `tests/uctx_layout.c`,
прогнанная на плеере, даёт раскладку без `$k0` и `$k1`: между `$t9` (+240) и
`$gp` (+264) нет смещений 248 и 256, то есть в `ucontext` этих регистров нет
вовсе. Отчёт печатал `regs[26]` и `regs[27]` — то есть **разрыв в раскладке**,
и ноль был выдан за «регистр равен нулю».

Это ровно тот класс ошибки, что запрещён правилом: значение, которое могло не
быть записано, обязано иметь метку «недействительно». Здесь метки не было, и
из неё выросла целая цепочка рассуждений.

Что сделано:

* `$k0`/`$k1` **не печатаются** — вместо них выводится
  «ОТСУТСТВУЮТ в кадре сигнала (измерено)»;
* номера регистров `R_K0`/`R_K1` удалены из кода: читать нечего;
* **откачена** подмена `$k0` при запуске потока, добавленная на этом основании.

Остаётся достоверным: `si_addr` = 0 или 4 при `SIGSEGV`, то есть сбой по данным
почти по нулевому адресу; и `$ra` = `0x08ABD010`, то есть сбой происходит
сразу после возврата из `CpuResumeIntr` (вызов 7, стаб `0x08AD2E54`). В какой
именно инструкции — установить нечем: PC для `SIGSEGV` не извлекается.

## Сбой потока локализован: запись по нулевому `$k0`

Сбой оказался **не** там, где предполагалось. Разбор загруженного кода гостя
(выгрузка через `psp-hle dump`, дизасм по адресам из выгрузки — файл неверен,
к нему применены релокации) дал точное место:

```
0x08ABD010  bltz v0,0x08ABD044
0x08ABD014  nop
0x08ABD018  sw s5,4(k0)     <- запись по $k0
```

В отчёте о сбое `k0 = 0x00000000`, `si_addr = 0` или `0x04`. Второе значение —
это ровно `$k0 + 4`, то есть та же инструкция при нулевом `$k0`.

**`$k0` не наполняется кодом гостя.** Разобрано около 2 КиБ: функция потока
`0x08ABCF68` и `0x08AA6A10` — записи в `$k0` (`$k0` = регистр 26) нет ни в
одной инструкции: ни `addu`, ни `addiu`, ни `lui`, ни `lw`, ни `sw`. То есть
значение приходит через возвращаемое значение импорта, а не через код.

### Поле по смещению 32 для SIGSEGV непригодно — проверено трижды

Поначалу два прогона показали `0x08ABD01C` и `0x08ABD018`, и это выглядело как
«PC минус 4». Из этого сделали вывод, что для `SIGSEGV` поле указывает на
инструкцию **после** сбоявшей, и стали вычитать 4.

**Вывод неверен.** Три прогона подряд при том же сбое дали:

| прогон | `si_addr` | поле +32 |
|---|---|---|
| 1 | `0x04` | `0x08ABD018` |
| 2 | `0x00` | `0x08ABD01C` |
| 3 | `0x04` | `0x08ABD014` |

`si_addr` тоже различается — значит гость падает в **двух разных местах**, а
поле просто колеблется около точки сбоя. Двух-трёх совпадений подряд для
закономерности недостаточно, и печать «PC в госте» была бы уверенным неверным
выводом. Код возвращён к прежнему поведению: слово читается только для
`SIGTRAP`, поле печатается без отождествления с PC.

**Локализует сбой `si_addr`** — для сбоя по данных он достоверен. Отчёт печатает
его отдельно с пояснением, и это то, что реально работает.

### Ложный вывод: «стабы идут подряд»

Промежуточно показалось, что стабы `0x08AD2E14 + 8*n`, и по этому был сделан
вывод «поток упал на 8-м импорте». На деле стабы **не подряд**: 7 вызванных
стабов заняли диапазон 304 байта при 7 стабах, а не 48. Порядок задаётся
обходом библиотек, и внутри библиотеки свой. Вывод отброшен.

Отчёт теперь печатает для каждого вызова **индекс импорта, адрес стаба и NID** —
вместе они связывают вызов с местом в разобранном коде гостя. Индекс
сквозной по всем библиотекам, ровно в том порядке, что и при построении
трамплинов. Раньше в отчёте был только NID, и обратного перехода к адресу в
госте не было.

### Возврат структуры вместо нуля

`GetModuleIdByAddress` (`0xD8B73127`) возвращает **указатель**, а обработчик
отдавал 0. Теперь возвращается настоящая 16-байтная структура **внутри
отображения гостя** (`tramp_base + GUEST_TRAMP_SIZE − 16`, свободный конец пула
трамплинов; наложения нет — трамплины занимают `0x54FC` из `0x10000`). Поле по
смещению 4 — указатель гостя на его собственный блок памяти, взятый из аргумента
`CpuSuspendIntr`.

Проверка на плеере: `$a0` вызова `CpuSuspendIntr` стал `0x08CB0FF0` вместо нуля,
и гость пошёл дальше. **Но `$k0` остался нулевым, и `SIGSEGV` сохранился** —
значит источник `$k0` не этот импорт, и гипотеза не подтвердилась. Правка
оставлена: возврат нуля вместо структуры заведомо хуже, а гипотеза ошибочна не
из-за неё.

Следующий предмет — выяснить, чем наполняется `$k0`. Ключ к нему теперь есть:
стаб `0x08AD2E4C` (вызов 6) — тот импорт, после возврата из которого гость
сразу пишет по `$k0`.

## Ошибка `ori` вместо `addiu` — и почему она стоила SIGILL

Это и был настоящий блокер последних прогонов.

Половины адреса вычисляются как `(v + 0x8000) >> 16` и `v & 0xFFFF`. Эта пара
складывается **`addiu`**, чей непосредственный операнд расширяется знаком: при
`lo >= 0x8000` лишние `0x10000` съедаются. Но в трамплине стоял **`ori`**, у
которого расширения нет, — тот же расчёт давал адрес, завышенный на `0x10000`.

Замерено на плеере:

| | `lui` | младшая половина | собирается | правильно |
|---|---|---|---|---|
| `fn` | `0x2AAB` | `0xB3C4` | `0x2AABB3C4` | `0x2AAAB3C4` |
| `$gp` | `0x2AAD` | `0x8010` | `0x2AAD8010` | `0x2AAD0010` |

Вызов `hle_import` уезжал на `0x10000` выше — в `.rodata`, где по этому адресу
лежат данные. Отсюда и `SIGILL`, и «ноль обработанных импортов»: первый же
вызов уходил не туда.

**Это же объясняет старую загадку с «инструкцией» `64615F69`.** То были байты
по адресу `0x2AABB3C4` — то есть по неверному адресу вызова. Диагностика не
врала: она показывала не PC, а место, куда трамплин действительно прыгнул.
Тогда это сочли мусором в данных; на самом деле это была первая улика.

Ошибка была видна на код раньше, чем на плеере, но не гейтом: `objdump` не
отличает код от данных (см. ниже), а строковая сверка в гейте появилась только
после. Теперь адрес проверяется **смыслом** — пересборкой пары так, как это
делает процессор, для `addiu` и для `ori` раздельно.

## Выгрузка окна загруженного гостя

`psp-hle dump <файл> <адрес_hex> <длина_hex> <куда>` — выгружает байты из
отображения гостя **после применения релокаций**. Готовить это из обработчика
нельзя (там нет вызовов), и не нужно: `guest_load` работает до `fork`, поэтому
у родителя уже есть ровно то отображение, которое видел потомок.

Зачем: дизасм файла неверен. Замер: в файле `lui v0, 0x002D`, в памяти
`lui v0, 0x08AD`. И `objdump` без символьной таблицы показывает в модуле
целую полосу `jr $ra; nop`, которой в загруженном образе может не быть.

Разбор окна делается подстановкой выгруженных байтов в расшифрованный PRX:
`vaddr = адрес − 0x08804000`, сегмент один, `vaddr` относительный.

## Что показал разбор загруженного кода

Все `jal` в окне идут **в стабы импортов** — `0x08AD2E4C`, `0x08AD2E54`,
`0x08AD2EC4`, то есть в наш диапазон `0x08AD2E14 .. 0x08AD32AC`. То есть
`CpuSuspendIntr` и `CpuResumeIntr` (вызовы 6 и 7) берутся именно оттуда, и
механизм подмены стабов работает.

Дальше функция с `beqz $k0` уходит в ветку «параметра нет» и готовит вызов
ещё одного импорта. Где именно происходит прыжок по нулю — не установлено,
потому что PC недостоверен (см. выше).

## Противоречие, которое не разрешено: `args[1]` не равно `$a1` (замер 2026-10-06)

Два независимых измерения дают разные значения для второго аргумента
`CreateThread`, и оба выглядят правдоподобно. **Какое из них указывает на дефект —
не установлено.**

Измерение А — код гостя в **загруженном** образе (`psp-hle dump`,
`0x08ABCE90..0x08ABCF90`):

```
8abcee8: lui   v0,0x8ac
8abcef8: addiu a1,v0,-12440     <- a1 = 0x08ABCF68
8abcf38: jal   0x8ad2f7c        <- вызов CreateThread
```

Между `0x8abcef8` и вызовом `$a1` **не пишется ни одной инструкцией**
(ветвления `beqz` идут мимо). Значит `$a1` = `0x08ABCF68`, и это подтверждается
тем, что по этому адресу начинается настоящая функция с прологом
`addiu sp,sp,-1008`.

Измерение Б — рантайм на плеере:

```
3: импорт 109  стаб 0x08AD2F7C  NID 0x446D8DE6
    $a0=0x08ACBBC8  $a1=0x08ABCF40  $a2=0x00000020  $a3=0x00019000
    место вызова (адрес возврата) = 0x08ABCF40
    кадр: [$sp+0]=0x08ABCF40  [$sp+4]=0x00000000
```

`args[1]` совпало и с `$a1`, и с сохранённым в кадре `$ra` (`$sp+0`), при том
что `$a0`, `$a2`, `$a3` и все три стековых слота верны. Расхождение ровно
`0x28`.

Что проверено и дефектом **не является**:

- **Байты трамплина выгружены с плеера** (`dump 08CA3500 AC`) и разобраны. Раскладка
  кадра верна: `sw ra,0(sp)`, `sw a0,8(sp)`, `sw a1,12(sp)`, `sw a2,16(sp)`,
  вызов `addiu a1,sp,8`. Следующий трамплин начинается с `addiu sp,sp,-64`,
  то есть кадр не наезжает.
- **`$ra` в отчёте верен.** Прежняя запись «адрес возврата завышен на 4» была
  ошибкой арифметики: `jal` в `0x08ABCF38` даёт `$ra` = `0x08ABCF38 + 8` =
  `0x08ABCF40`. Ровно то и напечатано.
- **Дизасм файла непригоден.** В файле `lui $3,0x2d` даёт `$a0` = `0x08AD7BC8`,
  в загруженном образе `0x08ACBBC8` — расхождение `0x20000` на `HI16`.
  Прежний разбор функции потока был сделан по файлу и потому неверен;
  правильный инструмент — `psp-hle dump`, как и записано в `AGENTS.md`.

## РАЗРЕШЕНО: загадка `$k0` и `args[1]` (Ghidra, 2026-10-07)

Оба вопроса закрыты независимым инструментом — **Ghidra 12.1.4 с расширением
ghidra-mcp**, гость загружен как `MIPS:LE:32:default`, 9282 функции,
автоанализ выполнен.

### 1. Гость передаёт правильный адрес входа. Мы читали не тот.

Декомпиляция функции, содержащей вызов `CreateThread` (создана вручную по
адресу `0x002b8eac`, тело 188 байт):

```c
uVar1 = FUN_002cef7c(s_user_main_002d7bc8, FUN_002b8f68,
                     DAT_0030b5e4, DAT_0030b5e0 << 10);
```

Второй аргумент — `FUN_002b8f68`, то есть гостевой `0x08ABCF68`.

Это **второй независимый источник**, подтверждающий выгрузку загруженного
образа (`psp-hle dump 08ABCE90 100`):

```
8abcee8: lui   v0,0x8ac
8abcef8: addiu a1,v0,-12440     <- a1 = 0x08ABCF68
8abcf38: jal   0x8ad2f7c
```

Итог: **гость прав, наш рантайм неправ.** `args[1]` = `0x08ABCF40` — это
адрес возврата (`0x08ABCF38 + 8`), а не адрес функции. Дефект в захвате
аргументов на нашей стороне; запускать гостя с `0x08ABCF40` нельзя, это
середина чужой функции.

### 2. Загадка `sw s5,4(k0)` снята: `$k0` — это пятый аргумент

Декомпиляция настоящей точки входа потока `FUN_002b8f68` (624 байта,
10 вызовов):

```c
undefined4 FUN_002b8f68(int param_1, int param_2)
{
  ...
  if (-1 < iVar3) {
    *(undefined1 **)(in_k0 + 4) = local_3a0;
```

`in_k0` — регистр `$k0` на входе функции, то есть **пятый аргумент** по
соглашению o32. Гость **читает `$k0` как указатель и пишет по нему со
смещением 4**. Во всём теле функции другое обращение к `$k0` отсутствует
(проверено: ровно одно упоминание, кроме объявления).

**Это в точности `sw s5,4($k0)`**, который мы искали по всему образу и не смогли
объяснить: записи `$k0` в коде гостя нет, значение приходит через аргумент —
теперь известно, через какой именно.

### 3. Наш рантайм поступает здесь правильно

`guest_enter` уже передаёт пятым аргументом `g_thread_info_addr(NULL)`, то
есть кладёт в `$k0` указатель на подделку структуры внутри отображения
гостя. Это ровно то, чего ждёт код. Значит:

- `GetModuleIdByAddress` и `g_thread_info_addr` — **не лишние**, они обслуживают
  `$k0`. Прежний вывод «подделка структуры бесполезна» (проверён A/B) касался
  только симптома, а не назначения;
- причина падения — **не `$k0` сам по себе**, а запуск с неверного адреса.

### 4. Побочно подтверждено расхождение файла и загруженного образа

Ghidra разбирает **файл** и видит первый аргумент как `s_user_main_002d7bc8`,
тогда как в загруженном образе на том же месте `0x08ACBBC8` — расхождение
`0x10000` на `HI16`. То есть Ghidra попадает в ту же ловушку, в которую попал
я вчера. **Для анализа гостя файл непригоден, нужен `psp-hle dump`.**

### 5. Осталось unexplained: значение `$k0` при вызовах импортов

В отчёте `$k0` = `0x001F0818`, `0x001F3418`, `0x001E2C1E` — узкая полоса
`0x001Exxxx..0x001Fxxxx`, это **не** адрес в отображении гостя
(`0x08804000..`).

Частично разобрано: точка входа модуля `FUN_002bbc3c` (420 байт) `$k0`
**не использует вовсе** — поиск по декомпиляции не дал ни одного употребления.
Значит нули в фазах модуля (вызовы 1..4) безвредны, а полоса `0x001Exxxx` —
мусор, оставляемый нашим же C-кодом `hle_import` между вызовами.

**Не объяснено:** вызов 5 — единственный, сделанный из потока (pid 1453), и
там `$k0` = `0x001FA81E`, тогда как `guest_enter` для потока передаёт
`g_thread_info_addr(NULL)`, то есть адрес внутри отображения гостя около
`0x08CB0FF0`. Это прямое противоречие: заданное значение не дошло. Требует
отдельного замера — где теряется `$k0` между входом в поток и первым импортом.

Проверять это Ghidra надёжнее нашего `find_k0.py`: тот инструмент уже один раз
оказался неполон (не знал `move` через `sll`, `movz`, `movn`), значит
отрицательный вывод «гость не пишет `$k0`» на его основании может быть неверен.

## ПРОВЕРЕНО: захват аргументов исправен; расходится гость (2026-10-07)

Одно- переменный эксперимент: в слот `+12` кадра трамплина положен **`$a2`
вместо `$a1`** (раскладка кадра не менялась, все смещения заняты).

Проверено, что правка попала в бинарник на плеере — выгрузка трамплина
побайтно, первое слово `0c 00 a6 af` = `sw $a2,12($sp)`.

Разбор всего кадра (`args[i]` — индекс в массиве, реальное смещение от
`$sp` гостя на `8 + 4*i`):

```
args[-2] = 0x08ABCF40   сохранённый $ra        ✓
args[-1] = 0x00000000   промежуток кадра
args[ 0] = 0x08ACBBC8   $a0                     ✓
args[ 1] = 0x00000020   подставленный $a2      ✓ СРАБОТАЛО
args[ 2] = 0x00000020   $a2                     ✓
args[ 3] = 0x00019000   $a3                     ✓
```

**Вывод: запись в слот `+12` и чтение из него исправны.** Подстановка видна
в отчёте, соседние слоты верны, путь «трамплин -> `hle_import` -> снимок ->
печать» не имеет дефекта.

Отсюда следует неприятное: раз наша сторона верна, то **до подмены в слоте
`+12` лежал настоящий `$a1` гостя, равный `0x08ABCF40`** — адресу возврата,
а не `0x08ABCF68`, который показывают оба независимых статических разбора
(выгрузка загруженного образа и декомпиляция Ghidra).

**Значит расходится гостевая сторона, а не наша.** Оба статических разбора
сходятся между собой, но не с динамикой — это классический признак того, что
по разбираемому пути до вызова есть **другая ветка**, которую статический
анализ не показал: `$a1` мог быть установлен на `0x08ABCF68` в одном пути, а
вызов достигается другим, где `$a1` уже перезаписан.

Требуется проверка: есть ли у стаба `0x08AD2F7C` другие ссылки помимо
`0x08ABCF38`, и какой регистр `$a1` на каждой из них. Инструмент для этого —
Ghidra (xref к `0x08AD2F7C`), а не повторный разбор вручную.

Диагностика `args[-2]`, `args[-1]` и полный кадр оставлена в коде: она
самокалибрующая и стоит почти ноль, а уже дала этот результат.
