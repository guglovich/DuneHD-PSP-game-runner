# Старт потока гостя: где мы оказались

Дата: 2026-10-11. Сборка `8f0563a2f18b80d4270686c5ad4fdff8`.

## Произошло

Рабочий поток гостя **дошёл до кода гостя впервые**. Метки обоих потоков
стоят:

```
gmark_main=0x47554554
gmark_worker=0x47554554
stk=2D1A80B0
k0 =2D1A7FB0      (= stk − 256, модель PPSSPP)
```

И кадр сбоя впервые целиком в **госте**:

| поле | значение | смысл |
|---|---|---|
| `pc` | `0x08AD75F4` | адрес образа гостя, не наш |
| `ra` | `0x08A9C9C4` | адрес образа гостя |
| `sp` | `0x2D1A7CC0` | `sp_top − 1008` = кадр гостя |
| `s7` | `0x2D1A80B0` | адрес блока контекста, гость его нашёл |
| `t1` | `0x08A9C958` | запись точки входа, ещё не затирана гостем |

## Две ошибки, которые это открыли, и почему их не видно было

### 1. Блок контекста затирал кадр потока

При `sp = sp_top − 16` кадр `worker_thread` (56 Б) занимал
`[sp_top−72, sp_top−16)`, а блок контекста (256 Б) — `[sp_top−256, sp_top)`.
Кадр лежал **целиком внутри блока**, и обнуление блока стирало `gp`, `ra`,
`s0…s4`.

Как выглядело: `lw gp,24(sp)` дал `0`, следующий `lw v0,-32588(gp)` обратился
по `0xFFFF8074` и дал `SIGBUS`. Сигнал и ненулевой `$pc` внутри
`worker_thread` выглядели как «гость исполняется не там».

Из `FillStack` PPSSPP был взят блок, но не взят `$sp`: там `SP = stack_top −
256`, `K0 = SP`. Правка — начальный `$sp` = `sp_top − THREAD_CTX_SPAN`, `arg`
остаётся `sp_top`.

### 2. Метка была общей на оба потока

Общая переменная дала ложный ответ «гость введён»: её успевал ставить главный
поток (он действительно входит и делает четыре вызова импортов), а сбой был в
рабочем. Метки разведены: `gmark_main`, `gmark_worker`.

## Текущий блокер — НАЙДЕН

Гость зовёт `strlen` по **нулевому** указателю. Код, выгруженный с плеера:

```
08ad75f4: lb    a2,0(a0)
08ad75f8: beqz  a2,08ad7610
08ad7600: addiu a0,a0,1
08ad7604: lb    a2,0(a0)      ← сбой, a0 = 0
08ad7608: bnezl a2,08ad7604
```

### Причина: точка входа — `main(argc, argv)`, а мы клали id потока

`0x08A9C958`, вход воркера:

```
 8a9c988: beqz  a2,0x8a9c99c
 8a9c9a8: blez  s3,0x8a9c9e8     # s3 = $a0 → нулевой argc пропускает разбор
 8a9c9b8: move  a0,s0            # s0 = $a1 → argv
 8a9c9bc: jal   0x2d35f4         # strlen; после релокации = 0x08AD75F4
 8a9c9c0: addiu s4,s4,1          # ra = 0x8a9c9c4 — как в дампе сбоя
 8a9c9cc: subu  v1,s0,s2         # argv_end − argv
 8a9c9d4: slt   v0,v1,s3         # цикл пока count < argc
```

Значит `$a0` = `argc`, `$a1` = `argv`. Мы передавали `$a0` = идентификатор
потока, `$a1` = 0 → `strlen(0)`.

Исправление: `$a0`/`$a1` берутся из третьего и четвёртого аргументов
`sceKernelStartThread` (`args[2]` = argc, `args[3]` = argv).
Идентификатор потока гостю доступен из `k0 + 0xc0`.

### `finished = 1` — аномалии нет

Флаг писателей имеет **три**, не один. Кроме `guest_thread` его ставит цикл
ожидания `!plat_thread_alive(g_guest_pid) && !guest_threads_alive()`.
То есть `finished=1` означало «оба гостевых потока мертвы», а не ранний возврат
главного потока. Гипотеза об «неинициализированных глобалах» снята.

## Инструмент: `tools/gdis.py`

Дизассемблирует гостя по рантайм-адресу локально. Разбирает `PT_LOAD`: у
модуля `p_offset = p_vaddr + 0x80`, и тождество `адрес − guest_base` даёт
осмысленный, но **чужой** вывод.

Проверен на эталоне — дизасм `0x08AD75F4` совпал с выгрузкой с плеера байт в
байт.

Файл гостя: `tmp/real/guest.elf`, взят с устройства, md5
`27e8339e78430eaee2932806d870196b`, 0x482204 Б.
**`tmp/real/EBOOT.dec.BIN` — другой файл (0x55a7e8), путать нельзя.**

## Текущий блокер — ГОСТЬ УХОДИТ В ЧУЖУЮ БИБЛИОТЕКУ

`jal 0` по `0x08A9CA00` и `0x08A9CA18` ведёт гостя на `0x08000000`.

У `jal` цель = `(pc & 0xF0000000) | (поле << 2)`, поле ноль → ровно
`0x08000000`. А по этому адресу в `shell` уже отображена **чужая
разделяемая библиотека**:

```
maps0800=r-xp 00000000 fe:08 18096032   /tango3/firmware/lib/libduneutil.so
```

То есть гость исполняет `libduneutil.so`, а не свой код.

### Подтверждено двумя независимыми способами

1. **Измерением карт процесса** — приведённая строка.
2. **Поведением:** подстановка `$k0 = 0x08B04000` в трамплин (вместо
   настоящего адреса контекста) дала `tramp_k0=0x08B04000`, а `si_addr`
   остался нулём. Запись идёт не через наш `$k0` — его затирает чужой код.

Согласуется и с остальным: рабочий поток не сделал **ни одного** вызова
импорта, а сбои «блуждают» по чужим адресам.

### Что при этом сделано правильно

* Стабы импортов подменены верно: `j` из `.lib.stub` уходят в наш пул
  трамплинов `0x08B06xxx` (проверено выгрузкой загруженного образа).
* Указатели в `.data`/`.rodata` собираются с нуля: у всех 22 020
  `R_MIPS_32` старший байт `0x00`.

### Гипотеза, не факт

Модуль, возможно, собран под базу `0x08000000`, а `PSP_USER_BASE` жёстко
задан `0x08804000` (`include/guest_load.h:30`), хотя отчёт печатает
`addr_free=yes`. **Не измерено.** Остальные 7492 `jal` внутри образа от базы
не зависят — их цели лежат в том же 256 МБ сегменте.

### Ошибка, которую я здесь допустил

Самодельный скан `.text` считал vaddr от начала сегмента, а нужно от
`p_offset` — разница `0x80`. Из-за этого «нашлась» третья `jal 0` по
`0x08B16E00`, которая на деле не код, а таблица (`sltiu`/`andi zero` подряд).
На этом смещении был построен вывод «единственный случай». Разбор `PT_LOAD`
в `tools/gdis.py` сделан верно — расходились именно сканеры.
