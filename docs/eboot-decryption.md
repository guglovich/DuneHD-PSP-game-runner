# Расшифровка ~PSP: как это сделано и что выяснилось

## Ответ на исходный вопрос

Спрашивалось: есть ли эталонный расшифровщик, или люди просто пользуются
базовым DISC_ID.

**Эталон есть, и он встроен в PPSSPP. DISC_ID не нужен вообще.**

Ключевой факт: ключ выбирается по четырёхбайтовому **тегу на смещении
0xD0** внутри самого EBOOT.BIN, а не по DISC_ID из PARAM.SFO.

```cpp
// Core/ELF/PrxDecrypter.cpp
{ 0xC0CB167C, g_keyEBOOT2xx, 0x5D, 0x5D },
```

Для розничного EBOOT тег всегда `0xC0CB167C`. Он однозначно выбирает и
ключ, и код KIRK (`0x5D`), и тип обработки (`pspDecryptType1`).

Схема с выводом `k1` из SHA1(DISC_ID) — это PSP 1.00, примерно 2004 год.
Давно заменена на KIRK со вшитыми таблицами ключей. Поэтому в свежем
PPSSPP нет ни генерации `k1`, ни tag-шифра: они не нужны, хватает таблицы.

Отдельной утилиты-расшифровщика нет: расшифровка встроена в загрузчик.
Всё остальное, что делают с образами, — это ISO/CSO/PBP и разбор ELF.

## Что использовано

`third_party/libkirk/` — выгружено из `ext/libkirk` репозитория PPSSPP:
AES.c, SHA1.c, amctrl.c, bn.c, ec.c, kirk_engine.c (около 140 КБ).
Лицензия GPL-2.0 (см. заголовок `kirk_engine.h`), распространяется на
проект.

Алгоритм взят из `Core/ELF/PrxDecrypter.cpp`, функция `pspDecryptType1`,
и таблица `g_keyEBOOT2xx`.

## Результат на реальном файле

```
Magna_Carta_Portable_JPN_PSP-DMU.iso -> SYSDIR/EBOOT.BIN
сигнатура ~PSP, модуль "softmax", тег 0xC0CB167C
-> "OK: контрольная сумма сошлась, магия ELF на месте"
   первые байты: 7f 45 4c 46 01 01
```

Две независимые проверки успеха, обе встроены в инструмент:

1. **контрольная сумма SHA1 заголовка сошлась** — значит ключ верный;
2. **первые байты — магия ELF** — значит результат действительно ELF.

Без правильного ключа не выполняется ни то, ни другое.

## Заголовок ~PSP подтверждён

Структура взята из `Core/ELF/PrxDecrypter.h`. Ключевые поля совпали с
наблюдениями, сделанными до их нахождения:

```
0x0A modname[28] = "softmax"     <- мы это установили эмпирически первым
0x28 elf_size    = 5 613 544
0x2C psp_size    = 5 613 888     <- ровно размер файла
0x30 entry       = 0x002B8EAC
0x34 modinfo_offset = 0x002CF488
0x3C seg_align[0]  = 16
0xD0 tag         = 0xC0CB167C    <- определяет ключ
```

## Что выяснено про импорты

Разобран расшифрованный файл (`tools/elf_imports.py`):

```
тип ELF: 0xFFA0 (PRX), машина MIPS, entry 0x002B8EAC
перевод адресов: file = vaddr + 0x54
модуль "softmax", gp = 0x0038A310
стабы: 0x002CF2C8 .. 0x002CF430 (360 байт)
```

Пример: `sceDisplay` — шесть NID, ни одного текстового имени функции.
Уникальных NID 147 из 147, то есть совпадений нет.

**Отсюда следует важное для проекта:** имена библиотек есть (они читаются
как строки), а имена функций — **нет**. Чтобы понять, что делает каждый
стаб, нужен внешний справочник NID. Без него подменять вызовы нечем.

## Что уже можно сделать без справочника NID

Работать с остальным: ELF разобран, точки входа и области известны,
`.rodata.sceNid` (1728 байта) содержит таблицу NID самой игры.

## Что нужно дальше

1. **Справочник NID.** Без него подмена системных вызовов невозможна в
   общем виде. Варианты: взять таблицу из эмулятора, из отладочных
   символов, или восстановить сопоставление по косвенным признакам.
2. Подменить стабы по назначению. Проверено, что механизм работает: на
   синтетическом образе гостевой вызов дошёл до хостской функции.
3. **Перевод адресов при загрузке.** Файл линкован от нуля
   (`p_vaddr = 0`, `entry = 0x002B8EAC`), настоящая база — `0x08804000`.
   Значит при загрузке адреса надо сдвигать на базу, а `dlopen` не подойдёт
   без пересборки в `ET_DYN`.

## Грабли, на которые уже наступили

* **Адреса в `.rodata.sceModuleInfo` — виртуальные, а читать надо по
  смещению.** Перевод `file = vaddr + 0x54` берётся из `p_offset - p_vaddr`
  программного заголовка. Без него читается мусор, который выглядит как
  осмысленные данные: имя модуля превращается в `ower...sceUtility`,
  `stub_top` — в `0x44656373`, и дальше разбор падает на чтении вне файла.
  В `tools/elf_imports.py` проверка границ обязательна, чтобы это
  выдавало ошибку, а не пустоту.
* **Имя модуля читалось по смещению 0x0A, а не 0x0C** — это было замечено
  на файле до того, как найдена структура.
* **Утилита искала EBOOT.BIN только в `USRDIR`** — у розничных игр он
  в `SYSDIR`. На синтетическом образе это не проявлялось.
