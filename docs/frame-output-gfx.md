# Вывод кадра: GFX доступен, устройство открывать не нужно

Источник: `Projects/Dune Max/docs/graphics-capabilities.md` и
`docs/em8xxx-driver.md`. Здесь — что из этого следует для нашего HLE-рантайма,
с проверкой на **живом** бинарнике `shell`, снятом с плеера.

## Главное: мой прежний вывод был неверен

Ранее записано было: «и ввод, и вывод кадра упираются в одно ограничение —
устройства держит `shell`». Для ввода это верно. **Для вывода — неверно.**

`/dev/em8xxx0` действительно держит `shell`, но вывод кадра через него **не
требуется**: `shell` экспортирует функции GFX, а команда уходит не в регистры
из постороннего процесса, а в буфер в DRAM, который исполняет DSP.

То есть запись в регистры GFX из чужого процесса (инцидент 4 из
`Dune Max/docs/bug-dvi-no-video.md`) **сюда не относится**. Это тот же
конвейер, что работает при видеовоспроизведении.

## Проверка на живом бинарнике

`shell` взят с плеера (`/firmware/bin/shell`, 10 704 252 Б) и разобран
локально. Только чтение, устройства Sigma не открывались.

**Экспорты на месте — 28 штук**, в том числе:

| экспорт | размер |
|---|---|
| `MY_GFX_FillRectangle` | 188 |
| `MY_GFX_CopyRectangle` | 232 |
| `MY_GFX_CopyRectangleBlendColor` | 248 |
| `MY_GFX_CopyAndScaleRectangle` | 196 |
| `MY_GFX_DisplayPicture` | 76 |
| `MY_GFX_Surface` | 132 |
| `MY_GFX_start_batch` / `commit_batch` / `end_batch` | 36 / 92 / 116 |
| `MY_GFX_wait_all_commands_to_be_finished` | 240 |
| `SEND_GFX_COMMAND` | **2448** |

**Проверка границ в `SEND_GFX_COMMAND` подтвердилась дословно.** Адрес
`0x00561948`, начало функции:

```asm
00561984:	addiu	s4,a0,-4292      # s4 = код - 0x10C4
00561988:	sltiu	v0,s4,408        # допустимо s4 < 408 = 0x198
00561994:	bnez	v0,00561bf4      # вне диапазона — на ошибку
```

Диапазон `[0x10C4, 0x125B]` — ровно как задокументировано.

**Механизм ленивого связывания подтверждён.** `shell` собран с glibc
(`libc.so.6`, `libdl.so.2`), в `NEEDED` есть `libphp5.so` и
`libskia_sigma.so`, и у обеих **ноль секций `.rel.text`**. Значит неопределённые
символы разрешаются при первом вызове, когда глобальная область уже полна, —
включая экспорты main-бинарника.

Следствие: `.so`, положенная рядом с плагинами, может звать `MY_GFX_*` и
`SEND_GFX_COMMAND` напрямую. Это не патч прошивки и не форк.

## Отсюда архитектура: рантайм живёт ВНУТРИ `shell`

Это меняет и устройство ввода. Если наш HLE — библиотека, загруженная
`shell`ом, то мы работаем **в его процессе**:

* GFX-вывод: зовём `shell`-овские экспорты напрямую;
* ИК-ввод: `/dev/ir` держит `shell`, а мы — это `shell`, значит `open()` из
  нашего кода не посторонний.

Оба блокера снимаются не обходом ограничения, а тем, что мы перестаём быть
посторонним процессом.

```
плагин .so, загружаемый shell'ом (рядом с плагинами duneext)
└── HLE-рантайм
    ├── гость: EBOOT, mmap по 0x08804000, релокации, подмена 147 стабов
    ├── HLE: sceKernel* (потоки и семафоры), sceGe*, sceDisplay*
    ├── sceDisplaySetFrameBuf → отдать буфер гостя в GFX
    └── sceCtrl* / /dev/ir → кнопки
```

## Как именно отдать кадр PSP в GFX

PSP рисует кадр software-вейбойзером GE в линейный буфер в RAM
(`sceDisplaySetFrameBuf` задаёт адрес и формат, `sceGe*` рисует). Дальше
нужно показать этот буфер на экране.

Примитивы, которые для этого нужны, и их аппаратные опкоды:

| шаг | примитив | опкод |
|---|---|---|
| задать формат цвета | `ColorFormat` | `0x06` |
| привязать буфер как поверхность | `MY_GFX_Surface` / `surface` | `0x07` |
| скопировать с масштабированием | `MY_GFX_CopyAndScaleRectangle` / `replace` | `0x05` |
| вывести на экран | `MY_GFX_DisplayPicture` / `display_picture` | `0x0e` |
| дождаться кадра | `MY_GFX_WaitForPicture` / `wait_picture` | `0x0f` |

Ключевой момент: **`0x05 replace` копирует с масштабированием в одном
примитиве.** Кадр PSP 480×272 в 1080p — это масштаб ~4×, и он делается
железом, без участия CPU. Отдельно аппаратный scaler основного видео уже
подтвердил на живом плеере апскейл 320×240 → 1920×1080
(`Dune Max/docs/game-upscaling-verified.md`).

Для индексированного 8-битного пиксель-арта годятся `0x08 color_palette`,
`0x09 alpha_palette` и `0x0c key_color`: 256 цветов, прозрачность бесплатно,
данные по 1 байту на пиксель. Стоимость примитива не зависит от площади —
CPU не трогает пиксели.

## Что надо сделать в нашем рантайме

1. **Ничего для доступа к GFX.** Ни `open`, ни `ioctl`, ни работы с
   `/dev/em8xxx0`. Только вызов экспортов.
2. **Свой буфер для кадра — открытый вопрос.** В
   `graphics-capabilities.md` зафиксировано, что зона MM0 исчерпана
   (4,3 КБ свободно из 101,9 МБ) и «свой буфер из processes не выделить,
   надо использовать существующий». Расходится с нашим прежним замером
   «179 МБ свободно»: это, видимо, разные пулы — RAM процесса и память
   конвейера вывода. Что именно требует GFX для буфера кадра, надо проверить.
   **Расхождение не разрешено.**
3. **Форматы поверхностей не проверены** — 16/32 бита реально принимаются,
   не выяснено.
4. **Синхронизация через `wait_picture`** (`0x0f`) есть, но использование без
   гонок не выяснено. Для игры это существенно: без корректного ожидания
   результат недетерминирован по времени.

## Оговорка

Всё выше проверено **статически**, на живом бинарнике: экспорты на месте,
границы кодов совпадают, ленивое связывание возможно. Ни одна команда GFX
ещё не отправлялась — запись в регистры из постороннего процесса запрещена
инцидентом, а вызов экспортов `shell` на живом устройстве не проверялся.

Первый безопасный шаг: из нашей `.so` вызвать
`MY_GFX_start_batch` / `MY_GFX_FillRectangle` на маленьком прямоугольнике в
углу экрана и `MY_GFX_commit_batch` + `MY_GFX_wait_all_commands_to_be_finished`.
Одна заливка, без записи в регистры. Если экран не потеряет видео — путь
подтверждён, и дальше остаётся подменить `sceDisplaySetFrameBuf`.
## Разбор `gfx_lib.c` — снят с пула строк `shell`

**Канонический разбор — `Projects/Dune Max/docs/gfx-command-protocol.md`.**
Здесь только сводка и то, что влияет на наш код; при расхождении
правильным считать тот документ. Дублировать разбор в двух местах нельзя:
дельта таблицы уже разъезжалась именно из-за этого.

Путь сборки: `/190919/r11/player/src/common/gfx_lib.c`, **r11 от 19 сентября
2019 года**. Весь userspace-API графики — один файл.

### Точка входа

```c
int SEND_GFX_COMMAND(uint32_t code, void *args, uint32_t size);
```

`shell:0x00561948`, 2448 байт, линковка C, экспорт через `.dynsym`.
Она же `MY_GFX_*`-обёртки в `.dynsym`, значит доступна из библиотеки,
загруженной в `shell`.

### Протокол — сводка

| что | значение |
|---|---|
| диапазон кодов | `0x10C4…0x125B`, `idx = code − 0x10C4`, допустимо `idx < 0x198` |
| слотов всего | 408, именованных 49, реализовано **51** код |
| таблица обработчиков | `base + 0x7CA0`, `base = 0x00C50000`, 4 байта на слот |
| **дельта слота** | **`+0xD91B34`, значение знаковое** |
| `sizeof(Command)` | **56** байт |
| слот в буфере | **64** байта, шаг `count * 64` |
| команд в батче | максимум **32** |
| контекст | глобал `0x00DA0000`: `+0x53B4` глубина, `+0x53B8` счётчик, `+0x53BC` база буфера, `+0x53C0` текущий указатель |
| выравнивание буфера | 8 КБ, гранулярность 64 байта |
| отправка | `RUASetProperty(0x00C49C70)` + `RMMemcpy(0x00AB5B38)` |
| коды возврата | `7` — backpressure (повтор), `6` — ошибка, прочее → `MY_fatal_error_f` |

**Дельта `+0x05E51B34` — неверна.** Правильная `+0xD91B34`, значение
знаковое. Прежняя величина получилась сложением двух неверных
интерпретаций. Проверено на всех 51 заглушке: имя сходится в каждой.

Обработчик — четыре инструкции:

```asm
lw    $2, -0x7fe8($gp)     # base
b     0x561e84             # общий путь
addiu $fp, $2, 0x75f0      # $fp = &"Close"
```

Заглушка только ставит `$fp` на имя команды. **Логики у отдельных кодов
нет** — она одна, различается именем.

### Правило: буфер `args` обнулять целиком

`SEND_GFX_COMMAND` копирует `args` как есть, ровно `size` байт. Часть полей
уже `u32`, а часть — **один байт**: в `MY_GFX_Surface` это `args[2]`, который
пишется инструкцией `sb` по смещению `+8`, то есть определён только младший
байт слова. Три старших байта остаются тем, что лежало в буфере.

Команды с байтовыми полями: `0x10CB +8`, `0x10CE +32`, `0x10D7 +28`,
`0x10D8 +40`. У `FillRectangle` байтовых полей нет, но правило действует и
для неё — обнуление стоит один вызов `memset`.

Реализовано в `gfx_build_fill_rect` и `gfx_build_surface`; гейт
`tests/gfx_command_test.c` проверяет, что хвост за полезной частью нулевой и
что все четыре байта байтового поля нулевые. Проверено, что гейт ловит
подстановку мусора в старшие байты.

### `Surface` (`0x10CB`) — обёртка с кэшем

```c
int MY_GFX_Surface(int engine, int a, int b)      /* 0x562364 */
{
    int *rec = (int *)(gfx->surfaces + engine);   /* ctx + 0x5394, шаг 8 */
    if (rec[0] == a && rec[1] == b) return;       /* состояние не изменилось */
    rec[0] = a; rec[1] = b;
    SEND_GFX_COMMAND(0x10CB, args, 24);           /* args[2] — ОДИН байт */
}
```

24 байта, шесть слов:

| смещение | поле |
|---|---|
| +0 | engine |
| +4 | b |
| +8 | ноль, определён только младший байт |
| +12 | a |
| +16 | ноль |
| +20 | ноль |

**Команда кэшируется в userspace:** повтор с той же парой `(a, b)` не
отправляется вовсе. То есть `Surface` меняет состояние движка и обязана идти
**первым перед рисованием**, как `glBindFramebuffer`. Отбрасывать повтор без
сверки нельзя — тогда рисование уйдёт не на ту поверхность.

Реализовано как `gfx_build_surface` с тем же кэшем.

**Расхождение в исходных данных, не разрешено.** `docs/gfx-argmap.txt`
сопоставляет слоты с регистрами как `+0<-$7, +4<-$6, +12<-$5`, тогда как
`docs/gfx-command-protocol.md` восстанавливает C как `args[0]=engine($4)`.
Это разные отображения: по таблице `args[0]` приходит из четвёртого аргумента,
а не из первого. Реализована версия из `gfx-command-protocol.md`, потому что
она даёт осмысленные имена полей. **Перед использованием на живом устройстве
соответствие слотов и регистров нужно подтвердить одним вызовом.**

### Глобалы: что где лежит

| адрес | что |
|---|---|
| `ctx + 0x5340` | **`buffer_addr`** — адрес кадрового буфера OSD |
| `ctx + 0x5344` | **`buffer_width`** |
| `ctx + 0x5390` | состояние GFX (`gfx`) |
| `ctx + 0x5394` | таблица поверхностей, шаг 8 |

Раньше `buffer_addr`/`buffer_width` были названы «поверхностью и форматом» —
это ошибка, опровергнутая по символам `.symtab`. Их читают `osd_initialize`,
`osd_flip`, `osd_at_flip` и ещё около сотни функций, то есть это кадровый
буфер OSD, а не состояние GFX.

### Нельзя читать `.bss` по адресам ELF на живом процессе

Наблюдение на плеере, **объяснения нет и не выдумывается**:

* первый `PT_LOAD` по файлу покрывает `0x400000–0xD30000`;
* живой RW-сегмент **на страницу ниже и на страницу короче**;
* `.bss` (`0xD94210–0xF1AC1C`) в `maps` **не попадает вообще** — с `0xD98000`
  начинается `[heap]`;
* `dd` из `/proc/<pid>/mem` отдаёт пустоту даже на странице `0x400000`.

Файл и процесс при этом один: md5 `3bde7c21…` совпадает, inode 11644084,
`/firmware/bin/shell` и `/tango3/…` — один файл; программные заголовки,
прочитанные прямо с плеера, дают те же байты, что локальный файл.

Следствие: разбор команд GFX сделан по `.text`, он в первом сегменте и не
затронут — **раскладка `FillRectangle`, поля и карта кодов остаются в силе**.
Но читать `.bss` по адресам из ELF на живом процессе нельзя: есть риск сдвига
на страницу для всего сегмента данных.

### Безопасность транспорта

Транспорт — буфер в DRAM плюс `RUASetProperty`. **Регистры из userspace не
пишутся, `/dev/mum0` не открывается.** Инцидент 4 сюда не относится.

Опасность в другом: команда уходит в DSP, а тот работает с MM0/MM1. Значит
нужно знать, **какую поверхность** мы отдаём. Это и проверяется первым.

### Раскладка `FillRectangle` — разобрана полностью

Эталонный вызов — `MY_GUI_paint_rect_no_blend` (`0x5613f0`):

```c
if (x <= 0 || y <= 0 || w <= 0 || h <= 0) return;
w2 = min(clip.x + clip.w, x + w) - max(clip.x, x);
h2 = min(clip.y + clip.h, y + h) - max(clip.y, y);
if (w2 <= 0 || h2 <= 0) return;

MY_GFX_FillRectangle(surf, fmt, x, y, w2, h2, color | 0xFF000000);
```

Команда `0x10CD` — пять слов, 20 байт:

| смещение | поле |
|---|---|
| +0 | x |
| +4 | y |
| +8 | ширина |
| +12 | высота |
| +16 | цвет |

Два вывода, важных для реализации:

1. **Отсечение целиком на CPU**, через `min`/`max` (`movn`). Clip-прямоугольники
   GFX не нужны вовсе.
2. **Альфа в старшем байте цвета.** Для непрозрачной заливки —
   `lui $3,0xff00; or color,$10,$3`, то есть `color | 0xFF000000`. Формат
   32 бита RGBA, «no blend» = альфа `0xFF`.

### Имена в обёртках — маркетинговые, протоколу не обязаны совпадать

| обёртка | код | имя в протоколе |
|---|---|---|
| `MY_GFX_FillRectangle` | `0x10CD` | FillRectangle |
| `MY_GFX_CopyRectangle` | `0x10DC` | MoveRectangle |
| `MY_GFX_CopyRectangleBlendColor` | `0x10D7` | SingleColorBlendRectangles |
| `MY_GFX_CopyRectangleBlendRectangle` | `0x10CE` | BlendRectangles |
| `MY_GFX_CopyAndScaleRectangle` | `0x10DF` | MoveAndScaleRectangle |
| `MY_GFX_CopyAndScaleRectangleBlendRectangle` | `0x10D8` | BlendAndScaleRectangles |

`0x10DF` = `MoveAndScaleRectangle`; карта `docs/gfx-code-map.txt` была права.

### Что реализовано у нас

`include/gfx_protocol.h` и `src/gfx_command.c`: константы протокола, имена
кодов, отсечение `gfx_clip_rect`, сборка `gfx_build_fill_rect` и отправка
`gfx_send_command` через `dlsym(RTLD_DEFAULT, "SEND_GFX_COMMAND")`.

Проверяется на хосте: `tests/gfx_command_test.c`, гейт в `make check`.
Проверено, что гейт ловит перестановку `x`/`y` и пропажу альфы.

Неизвестно по-прежнему: значения `surf` и `fmt` — первых двух аргументов
обёртки, они берутся из глобалов, а не из вызова.

### Что осталось неизвестным

1. **Значения `surf` и `fmt`** для первого вызова. Берутся из глобалов.
2. **Раскладка остальных команд** — размеры есть, имён полей нет.
3. **`RUASetProperty`** — формат вызова восстановлен, смысл полей нет.
4. **Три PLT-функции** (`0x4F7010` — запрос DRAM, `0x4F79A0` — лог,
   `0x4F6FD0`) не разрешились: их GOT-слоты не в `.rel.plt`. Побочно —
   `tools/resolve_got.py` на них даёт обрезанное имя `PLT]`, баг инструмента
   (инструмент в соседнем проекте, здесь не чинился).
5. **Кто вызывает `SEND_GFX_COMMAND` снаружи** — по-прежнему никто.
