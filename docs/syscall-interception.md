# Перехват системных вызовов PSP: что выяснено о платформе

Дата: 2026-10-04. Все утверждения проверены на живом плеере экспериментом,
не рассуждением. Исходники проб — `tmp/probe_*.c`, загрузка на плеер через
SMB, запуск через `ld-musl-mipsel.so.1`.

## Главный результат

**Гостевой код нельзя исполнить из самодельной страницы памяти.**

Это не ограничение сегментов и не выравнивание, и не запрет `PROT_EXEC`.
Это факт о ядре: код, размещённый ядром, исполняется, а код, размещённый
нашим `mmap`, падает.

**Но задача решена другим путём, и он проверен:** гостевой образ грузится
системным загрузчиком через `dlopen`, и тогда страницы создаёт ядро.
Подробности и результат — ниже, в разделе «Перехват доказан».

## Что проверено

| Эксперимент | Результат | Что это значит |
|---|---|---|
| `dlopen` `.so` + вызов функции | **работает**: `lib_answer()` → `0xC0FFEE` | код, размещённый ядром, исполняется |
| анонимный `mmap` `PROT_EXEC`, вызов `jr $ra; nop` | **SIGSEGV** | свой код из своей страницы не идёт |
| то же из `malloc` | **SIGSEGV** | не в способе получения страницы |
| `mmap` из файла, `PROT_EXEC` | **Illegal instruction** | и файловые отображения не годятся |
| выравнивание по 4 байта | адрес и так кратен 4 | выравнивание не при чём |
| размер, кратный 16 КиБ | падает | размер страницы ядра не при чём |
| фиксированный адрес `0x20000000` | страница создаётся, запись/чтение идут | отображение есть, исполнения нет |

Отдельно проверено, что запись и чтение из отображения работают: маркер
`0xDEADBEEF` записан и прочитан без ошибок. То есть страница валидна, но
исполнение из неё не разрешено.

## Следствие для дизайна HLE

Механизм, который я планировал — «гость прыгает в нашу C-функцию через `j`» —
**не реализуем**: для прыжка нужен исполняемый адрес хоста, но мы не можем
исполнять то, что сами разместили, а хост-функции живут в коде, который
загрузил `ld-musl`, то есть разместило ядро.

Остаётся рабочий и, что важно, **проверенный** путь: гостевой образ
загружается **системным загрузчиком** — как разделяемая библиотека. Тогда
его страницы создаёт ядро, и код исполняется. Это ровно тот случай, который
проверен: `dlopen` дал рабочую функцию.

### Проверено с гостевым файлом

```
dlopen("./libtest.so")            -> OK, функции вызываются
dlopen("/D/psp_launcher/games/EBOOT.BIN") -> "Exec format error"
```

Ошибка ожидаема и информативна: `EBOOT.BIN` — это `ET_EXEC` со своей схемой
адресов, а не `ET_DYN`. `dlopen` требует `ET_DYN` и отказывает. Значит
гостевой образ нужно готовить к загрузке заранее: пересобрать в
`ET_DYN`/`ET_DYN` с `-fPIC` и базой 0 (`-Ttext`/`-pie`), а адреса вида
`0x08804000` получать добавлением базы при разрешении символов.

## Что это меняет в плане

Раньше предполагалось: `mmap` гостя, запись через `memcpy`, вызов через `j`.

Теперь: **пересборка гостевого EBOOT.BIN в динамический объект**. Тогда:

1. `dlopen` даёт исполняемые страницы от ядра — механизм проверен;
2. импорты резолвятся штатным загрузчиком через NID — ровно то, что нужно
   для подмены системных вызовов, причём бесплатно;
3. точка входа вызывается как обычная функция;
4. ограничение `j` (24 бита) обходится тем, что всё лежит в одном
   загруженном образе.

Побочная выгода: резолвить импорты вручную не нужно. `dlopen` с
`RTLD_NOW` сам находит символы, и подмена сводится к тому, чтобы
предоставить свою библиотеку с этими именами.

## Перехват доказан на живом плеере

Механизм собран и проверен. Три части:

1. **гость** — обычный MIPS-код, собранный как `.so`, вызывает внешнюю
   функцию `sceKernelExitThread(7)`;
2. **хостская библиотека** — определяет функцию с тем же именем и печатает
   маркер перехвата;
3. **загрузчик** — грузит хостскую библиотеку **первой** с `RTLD_GLOBAL`,
   затем гостя с `RTLD_NOW`.

Вывод на плеере:

```
1. загружаем хостскую реализацию ./host_impl.so
   OK: 0x2aab3ec0
2. загружаем гостя ./guest_imp.so
   OK: 0x55633de0
3. гость нашёл импорт и вызывает точку входа 0x2aac0610
   гость вызывает sceKernelExitThread...
   >>> ПЕРЕХВАТ: sceKernelExitThread(7) — вызов гостя дошёл до нас
4. гость вернулся
```

Значит работают все три нужных свойства:

* гостевой код исполняется;
* системный вызов гостя доходит до хостской функции;
* порядок загрузки решает, чья реализация победит.

### Что именно пришлось сделать, чтобы заработало

Две ошибки, обе найдены на устройстве, не по чтению:

1. **`dlopen` требует `ET_DYN`.** Гостевой `EBOOT.BIN` — это `ET_EXEC`,
   и загрузчик отвечает `Exec format error`. Значит гостевой образ нужно
   пересобирать в динамический объект, а не грузить как есть.
2. **Глобальная переменная гостя должна быть определена, а не объявлена
   `extern`.** При `extern unsigned g_marker;` символ остаётся
   неопределённым, и `dlopen` падает на релокации до вызова точки входа:
   `Error relocating ...: g_marker: symbol not found`.

Обе ошибки относятся к подготовке гостя, а не к перехвату, поэтому сам
механизм перехвата оказался рабочим сразу.

### Свойства `dlopen`, на которые опирается подмена

* `RTLD_GLOBAL` на хостской библиотеке — символы попадают в глобальную
  область поиска, и гость находит именно их.
* `RTLD_NOW` на госте — все релокации проверяются при загрузке, поэтому
  отсутствующий символ обнаруживается сразу, а не при первом вызове.
* Имя символа у гостя должно **совпадать с именем в библиотеке PSP**.
  У настоящих игр это не текстовые имена вида `sceKernelExitThread`, а
  числа NID — их резолвит загрузчик PSP. Это отдельная задача: сопоставить
  NID с нашими функциями.

## Что надо проверить дальше

1. Брать настоящий EBOOT.BIN, извлекать из него таблицу импортов и
   получать список NID, которые игра реально использует.
2. Сопоставлять NID с нашими реализациями: нужен реестр вида
   NID → функция хоста.
3. Пересобрать гостя из настоящего EBOOT.BIN в `ET_DYN` и проверить, что
   он грузится и держит нужные адреса.
4. Ввод: кнопки по-прежнему приходят из процесса `shell`, это не решено.

## Отвергнутые гипотезы

Записано, чтобы не проверять повторно:

* **Ограничение 256 МБ для `j`** — настоящее, но не является причиной падений:
  падало даже тогда, когда хост и гость были в одном сегменте
  (`0x20000000`), и даже на `jr $ra`, который вообще никуда не прыгает
  по дальнему адресу.
* **Выравнивание** — адреса кратны 4, ничего не изменилось.
* **Размер страницы ядра 16 КиБ** — проба с размером, кратным 16 КиБ, падает
  так же.
* **`PROT_EXEC` вообще не работает** — неверно: `r-xp` в карте памяти есть,
  и код из `.so`, размещённого ядром, исполняется.

## Связанное ограничение

Ввод недоступен из своего процесса: `/dev/ir` держит `shell`, из постороннего
процесса `open()` даёт `Input/output error`. Подробнее — в `player-recon.md`.
Для игры на загруженном через `dlopen` образе это отдельная задача: кнопки
должны приходить из процесса `shell`.
